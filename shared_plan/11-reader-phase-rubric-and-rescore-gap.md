## 2. 原因（A）: ルーブリックにフェーズ軸が存在しない ── 主因

`src/lib/llm/prompts.ts:48` の `preDecisionOrPhotoShoot` の定義（逐語）:

> 内容が次のいずれかに限られる場合に true とする。(a) フォトウェディング・前撮り・後撮りなど、挙式・披露宴とは別に行う撮影そのものの話題。(b) 式場探し・式場見学・見積もり比較・日取り決定など、挙式する会場や日程を決めるまでの段階の話題。挙式当日の写真・映像（スナップ撮影、記録映像、エンドロール）は (a) に含めない——これは挙式・披露宴の中身である。式が既に決まっている前提で書かれた記事、あるいはどちらとも判断できない記事は false とすること。

この記事は (b) よりさらに上流の「**そもそも挙式するか／どんな規模・形式でやるか**」という実施可否・規模・形式の合意形成フェーズにある。(a)(b) のどちらにも該当しない。

コード・spec・プロンプトを「挙式するか」「やるかどうか」「規模」「形式」等で全検索した結果、この段階を指す属性・語彙はどこにも存在しない。**したがって LLM は定義通りに `false` を返しており、誤判定ではない。定義の穴である。**

この属性は「-3点の減点項目」ではなく、実質 **-15点のゲート項目**である点が重要:

```
preDecisionOrPhotoShoot: false → 12 + 3+2+2 = 19（理論最大）
preDecisionOrPhotoShoot: true  →  0 + 3+2+2 - 3 = 4（ゲートボーナス12を同時に失う）
```

`ceremonyDecision && !preDecisionOrPhotoShoot` というゲート条件により、この1ビットが 19 と 4 を分ける。**強支配不変条件の設計は正しく機能している。壊れているのは該当判定の網だけ**であり、スコア式に触れる必要はない。

### `ceremonyDecision=true` は現行定義下で「正解」である

`ceremonyDecision` の定義（`prompts.ts:41` 逐語）は「挙式・披露宴の中身の意思決定に効く（進行・タイムライン・演出・席次・席札・余興・スピーチ・BGM・装花・料理・引出物・ペーパーアイテム・挙式当日の写真・映像・ゲストの過ごしやすさ・当日段取り）」という**トピックの列挙**であって、読者フェーズの判定ではない。「家族向け和装神前式＋友人69名の洋装披露宴の2部構成」は式全体の「進行」に関する意思決定として列挙項目に当てはまる。

### 構造的欠陥の正体: 想定読者定義が判定項目から参照されていない

`src/lib/llm/prompts.ts:21-22` の `READER_PERSONA`（逐語）:

> 想定読者は、挙式日・会場が決まっており、衣装（ドレス・和装）もおおむね決まっている。これから決めるのは挙式・披露宴の中身である —— 進行とタイムライン、演出、席次と席札、余興、スピーチや余興の依頼、BGM、装花、料理、引出物、ペーパーアイテム、写真と映像、ゲストの過ごしやすさ、当日の段取り。この読者が求めているのは「何が人気か」ではなく「実際に式を挙げた人が、何を、なぜそう判断したか」である。

**この読者フェーズ定義を、6つの判定項目のどれ一つとして参照していない。** 読者定義はプロンプト冒頭の飾りになっており、判定項目に接続されていない。`preDecisionOrPhotoShoot` は本来「対象読者フェーズ外」を意味すべき属性なのに、実装上は「フォトウェディングと式場探し」という2つの具体例の列挙に縮退している。**本件はこの非接続の帰結の一例であり、個別の穴ではない。**

## 3. 原因（B）: 1位は17件の同点クラスタの中のくじ引き

実測（§5）で 19点が87件中17件。掲載順は `ORDER BY score DESC, publishedAt DESC, posts.id DESC`（`src/lib/db/query.ts:162`、spec.md §9.6）で、スコアによる足切り閾値は存在しない。つまり **1位が誰になるかは17件の中での掲載日時の運**。§2 を直してこの記事が沈んでも、次の19点記事が同じ理由で1位に来る。利用者の体感する問題は「この記事が1位」だが、システムの問題は「**1位に情報量が無い**」こと。

## 4. 原因（C）: 再スコア機構が「緑のまま」機能していなかった

`src/lib/llm/signature.ts:30-35` の `computeCurationSignature()` は `sha256("v" + CURATION_PROMPT_VERSION + "\0" + LLM_MODEL)` の先頭16文字を返す。入力は **`CURATION_PROMPT_VERSION`（`src/lib/constants.ts:60`、現在 4）と `LLM_MODEL`（`gemini-3.1-flash-lite`）の2定数のみ**。プロンプト文言そのもの・判定項目定義はハッシュ入力に含まれない（スコア重み定数の除外は `signature.ts:21-29` のコメントで意図的な設計判断として明記されている）。

`getStaleCurationCandidates()`（`src/lib/db/repository.ts:393-421`）は `posts.curationSignature` が null か `currentSignature` と不一致の行のみを再スコア対象として返す。

**実際に起きたこと**: コミット `a8d4f0f`（PR要素のenum化）は `src/lib/llm/prompts.ts` の `USEFULNESS_CRITERIA_RULES` を boolean 一律から3段階記述へ実質的に書き換えたが、`git show --stat a8d4f0f` に `src/lib/constants.ts` も `src/lib/llm/signature.ts` も含まれておらず、**`CURATION_PROMPT_VERSION` は 4 のまま据え置かれた**。コミットメッセージは `normalizePromotional()` による読み取り時の後方互換にのみ言及し、signature bump という選択肢が検討された形跡がない。

結果、本番87件の `signature` は**全件が同一値 `042b8b990a361b83`**（`sha256("v4\0gemini-3.1-flash-lite")` の先頭16文字と一致することを検証済み）。`promotional` が旧仕様 boolean のまま残っている行が **82件 / 87件**。

`scripts/backfill-usefulness.mjs` に `--force` 相当は存在しない（オプション解析は22行目の `const APPLY = process.argv.includes("--apply");` のみ）。対象は常に `getStaleCurationCandidates()` が決めるため、**版数を上げない限り `--apply` を付けても対象0件で無音成功する**。

spec.md は §8付近(140-142行)・§9.3付近(544-545行)・§9.5(610-611行)・§9.6(653-655行) で「signature不一致検出により自然に再スコアされる」と繰り返し書いているが、**「プロンプト文言や判定項目定義を変えたら `CURATION_PROMPT_VERSION` を手動でbumpしなければならない」という運用義務としての記述はspec.mdに存在しない**（bump履歴コメントは `src/lib/constants.ts:41-60` にのみある）。これが `a8d4f0f` の見落としを許した構造。

**この機構はデッドコードではない。正しく動くが、人間の手動bumpに100%依存しており、その依存が spec にも CI ゲートにも記述されていない。** AGENTS.md の「ゲートが緑であることと、ゲートが機能していることは別である」の実例である。

## 7. 実測の読み方

1. **`preDecisionOrPhotoShoot` は「定義された範囲内では」正しく機能している。** 17件が確実にスコア2〜4に沈んでいる。ゲート設計の失敗ではない。網の目が粗いだけ。
2. **上側の飽和（19点17件）は母集団の19.5%であり全体としては飽和ではないが、公開トップの1位は17分の1のくじ引きである。** ユーザー体験の面では致命的。
3. **判定パターンの二極化（上位2パターンで41.4%、全true/全false型）は、重み設計の解像度不足ではなく、分類器の出力自体に解像度が無いことを示唆する。** LLM が実質「良い記事／悪い記事」という単一軸1ビットしか返していない疑いがある。**もしこれが真なら、判定項目を何個足しても、重みを何段階にしても情報量は増えない。**
4. **下側の0点39.1%（34件）は「悪い記事が正しく沈んでいる」とは限らない。** プロンプト末尾の全体ルール（`prompts.ts:52` 逐語）「判断材料が本文抜粋に無い場合、各項目は true ではなく false とせよ。本文にあるだろうと推測して true にしてはならない。」を踏まえると、**本文抜粋が痩せていて何も判定できていない**可能性が同程度にある。後者なら収集パイプライン側の問題であり、スコアリングをいくら直しても解決しない。両者を区別する計測が必要。
5. **`promotional: heavy` が1件（1.1%）で、-4の分岐は実質死んでいる。** 82/87 が旧 boolean であることと合わせ、**enum化（`a8d4f0f`）の効果は一度も検証されていない**。
6. **§4 が示す通り、現在のデータ状態に関する我々の想定は既に一度外れている。** データを見ずに設計を進める根拠がない。

## 8. 段階設計

### Stage 0: 再スコア機構の修復 ── **最優先ブロッカー。これ無しに Stage 3 は無音で失敗する**

範囲:

- `CURATION_PROMPT_VERSION` の bump 運用を、人間の記憶ではなく機構で担保する。`scripts/check-spec-update.sh` が spec 未更新を pre-commit で warning する既存の前例に倣い、**`src/lib/llm/prompts.ts` が staged なのに `src/lib/constants.ts` の `CURATION_PROMPT_VERSION` が変わっていない場合に警告する**チェックを追加する方式を第一候補とする。
- あわせて spec.md に「プロンプト文言・判定項目定義を変更したら `CURATION_PROMPT_VERSION` を bump する」という**運用義務**を明文化する（現在 spec は再スコアが自動で起きるかのように書いており、これが `a8d4f0f` の見落としを許した）。
- signature の入力に `USEFULNESS_CRITERIA_RULES` の文字列ハッシュを直接含める案は**採らない**——無関係な整形変更でも全件再スコア課金を誘発するため。`signature.ts:21-29` の既存の設計判断（重み定数を除外した理由）と同じ論理。

完了判定: **意図的に `CURATION_PROMPT_VERSION` を変更し、`getStaleCurationCandidates()` が87件を返すことを確認する。** 確認後は版数を戻し、この段階では再スコアを実行しない。追加したチェックについても、`prompts.ts` だけを変更した状態を作って**実際に警告が出ることを確認するまで完了としない**（AGENTS.md「意図的に壊して実際に落ちることを確認するまで完了と見なさない」）。

### Stage 1: 計測 ── **大部分は実施済み（§6）。残タスク4件**

いずれも LLM 課金ゼロ・読み取り専用。

| 残タスク                                          | 目的                                                                                                                            | 完了判定                                                          |
| ------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------- |
| 19点17件の目視フェーズラベル                      | §2 の被害規模の確定。17件中何件が「実施可否・規模・形式フェーズ」か。1件なら定義拡張の費用対効果は低く、5件以上なら正当化される | 17件全件に人手ラベルが付き、該当件数が確定                        |
| 19点クラスタの `publishedAt` 分布                 | 1位がどれだけの頻度で入れ替わるか、17件が過去何日に散っているか                                                                 | 「1位が新着順の運である」ことの定量表現が本文書に載る             |
| 全false 30件の抜粋長分布                          | §7-4 の切り分け。「悪い記事が沈んでいる」のか「抜粋が痩せて判定不能」なのか                                                     | 全false群と判定成立群の抜粋長を比較し、どちらの仮説かが示される   |

不要になったもの: 旧boolean残存件数（82/87 で測定済み・Stage 3 の全件再スコアで自動解消）、未スコア件数（0件で確定）。

### Stage 2: ゴールデンセットと評価ハーネス ── 中心指標は「項目間の独立性検証」

範囲: ラベル定義書、評価コーパス（**40〜60件、層化**: 対象フェーズ内20 / 式場探し・撮影10 / 実施可否・規模・形式10 / 事業者色の強いもの（heavy候補を含む）10 / 境界例10）、評価スクリプト（URLから再取得 → 現行プロンプトで判定 → ラベルと突合 → レポート生成）。

**法務制約（絶対）**: ゴールデンセットは **URL＋人手ラベル＋原文の創作的表現を再現しない短い根拠メモ**のみを持つ。**記事本文（抜粋を含む）をリポジトリにコミットしてはならない**（spec.md §10 の本文非永続化）。評価時に毎回再取得する設計にすること。

**CI 方針**: 実ネットワーク＋LLM課金を伴うため **PR の CI ゲートには入れない**。`scripts/check-sources.mjs` / `scripts/check-oembed-contract.mjs` と同じく `.github/workflows/weekly-monitor.yml` または手動実行に置く（AGENTS.md「外部依存の監視は CI ゲートに入れない」に整合）。決定論的に vitest + coverage tier の対象にできるのは**ラベル読み込み・集計・レポート生成の純ロジックのみ**で、ネットワーク／LLM部分は明確に境界を切って対象外にする。

測定指標:

1. **項目間相関**（φ係数／Cramér's V）を LLM 出力と人手ラベルの両方で算出し**比較する**。人手ラベルでも相関が高いなら「良い記事は実際に全部満たす」＝正常。人手だけ混在パターンが出るなら**単一軸崩壊が確定**。
2. **パターンエントロピー比較**: 判定パターンのユニーク数・エントロピーを LLM 出力 vs 人手ラベルで比較（現状 LLM は22パターン／上位2つで41.4%）。
3. **条件付き精度**: 各項目の精度を他項目の真偽で層別。崩壊しているなら偏りが出る。
4. **本文抜粋長を共変量として記録**: 全false記事の抜粋長分布との突合（§7-4 の仮説の直接検証）。
5. **自己不一致率**: 同一入力を複数回流したときの判定の揺れ。**これが無いと後段のいかなる改善も有意かどうか言えない。** gemini-3.1-flash-lite は確率的であり、「本件1件が落ちた」は改善の証拠にならない。
6. per-criterion の precision / recall / 混同行列。特に `preDecisionOrPhotoShoot` の **recall** と `ceremonyDecision` の **precision** をベースライン値として確定させる。

完了判定: 上記がすべて測定・記録され、ベースラインが確定していること。

**タイムボックス**: ラベリングは人手時間を食う。40〜60件に区切り、「全カテゴリ網羅」ではなく「`preDecisionOrPhotoShoot` の recall と `ceremonyDecision` の precision、および項目間独立性を測れる最小構成」に絞る。完璧な評価基盤を作ってから直す、という順序に膨らませない。

### Stage 3: 定義改訂と再スコア ── **Stage 2 の結果による条件分岐あり**

#### 分岐条件

**単一軸崩壊が確認された場合（Stage 2 指標1・2）**: 定義拡張より**判定構造の分離を優先する**。具体案は、項目ごとに根拠を1行述べさせる（**原文の創作的表現を再現しない要約形式に限定**、spec.md §10）、あるいは相互に依存しやすい項目を別コールに分離する。いずれも1回のLLM呼び出しコストを押し上げるため、崩壊が実測で確認されてから判断すること。

**崩壊が確認されなかった場合**: 定義拡張に進む。`preDecisionOrPhotoShoot` の (b) を「式場探し・式場見学・見積もり比較・日取り決定**、および挙式するか否か・どの規模や形式で行うかを夫婦や両家で決めるまでの段階**」に拡張する。

#### 定義拡張時の必須事項

- **「内容が次のいずれかに*限られる*場合に true」という現行の限定節を絶対に外さないこと。** この1ビットは実質 -15 であり、偽陽性の代償が極めて大きい。「小規模婚を選んだ経緯に触れつつ、当日の演出も詳述する良記事」を巻き添えで沈めるリスクがある。

- **スコア式・重み定数・SQL・不変条件には一切触れない。** `tests/feed-order-parity.test.ts` と `tests/usefulness-score.test.ts` が無変更で緑のままであること自体が「式に手を出していない」ことの証明になる。

#### 手順（順序が重要 ── LLM課金を抑える要）

1. プロンプト改訂 → **ゴールデンセットで評価** → `preDecisionOrPhotoShoot` の recall が改善し、かつ `ceremonyDecision` の precision が低下していないことを確認。**差分が自己不一致率を超えていること**を有意性の条件とする。
