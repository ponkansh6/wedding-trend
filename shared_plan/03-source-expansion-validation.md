## 1. なぜ今これをやるか

「定番アーカイブ」レーン（`sourceType: "blog"`、`src/components/feed/feed-lane-classic.tsx`、
見出し「満足度の高い王道・定番」）に供給しているソースは、登録4件のうち**実質2件しか稼働していない**。

| 定数                   | 内容                                     | 状態                               |
| ---------------------- | ---------------------------------------- | ---------------------------------- |
| `GOOGLE_NEWS_QUERIES`  | 「結婚式 トレンド」「ウエディング 演出」 | 稼働                               |
| `NOTE_HASHTAGS`        | 結婚式準備 / 卒花 ほか 7 タグ            | 稼働                               |
| `HATENA_BOOKMARK_TAGS` | `[]`                                     | 無効（議論・炎上寄りで趣旨不一致） |
| `AMEBLO_BLOG_IDS`      | `[]`                                     | 無効（婚活・日記・店舗販促が混在） |

（`src/lib/constants.ts:192-261`）

単一ソース障害でレーンが枯れる構成であり、供給の細さは事実として存在する。
一方で「ソースを足せば良くなる」という前提は、本検証で**成立しないことが分かった**（§3）。
本計画は、ソースを足す前に何を確かめるか、そして候補を**どの条件で却下するか**を先に固定するためのものである。

## 3. 最重要の発見: 問題は「ソースの数」ではない

定番レーンの約束は「満足度の高い王道・定番」＝**エバーグリーン**である。
しかし稼働中の 2 ソースの性質は、

- **note** = UGC の体験談（新着順）
- **Google News** = 業界ニュースと PR（新着順）

であり、どちらも構造的にエバーグリーンではない。**新着順のフィードは定義上「定番」を出せない。**
ここにソースを何本足しても、この不一致は解消しない。

したがって本計画の第一歩は、ソース追加ではなく**レーンの候補母集団の確認**である（§5 の V0）。
定番レーンのランキング母集団が「直近 ingest ウィンドウ」なのか「`posts` 全体」なのかで、打つべき手が正反対になる。

- 直近 ingest のみを見ている場合 → 良質なエバーグリーン記事は次の ingest で押し出される。
  **ソースを増やしても定番性は一切改善しない。** retention / pin 機構を入れるか、レーン名を実態に合わせるのが正しい。
- `posts` 全体を見ている場合 → 在庫を増やす意味があり、ソース拡張が有効打になる。

## 4. 方式レベルの判断

### 4.1 本文 HTML スクレイピングは採用しない

§2.1 のとおり国内メディアは RSS を持たないため、取り込むにはスクレイピングが必要になる。
これを**採用しない**。根拠は 4 点。

1. **現行の法的ポジションは「RSS であること」に依存している。**
   RSS は媒体が自ら運用する opt-in の配信路で、title / excerpt / author / link は
   「リンク先へ送るために」提供されている。カードの excerpt が**媒体自身の要約**であることが、
   spec.md §10-1・§10-3 の実質的な担保になっている。HTML から本文を抽出した瞬間、
   excerpt は「配布を意図された要約」から「本文の創作的表現の切片」に変わる。§10 が守っているものそのものが崩れる。

2. **`hasSourceText` ゲートが反転する。**
   本文が取れるアダプタを1本入れると、これまで AI 要約の対象外だった記事群が一斉に要約対象になる。
   §10-4 は「原文テキストが取れない場合は生成しない」だが、スクレイピングは「取れるようにする」変更である。
   ゲートは技術的には正しく動いたまま、リスクだけが増える。
   **このリポジトリで実行しうる変更のうち、ゼロクリック化を最も直接的に進めるのがこれ。**

3. **robots.txt は十分条件ではない。**
   著作権法 47条の5（所在検索サービスの軽微利用）は、収集拒否措置が取られている場合に収集しないことを求めるが、
   robots.txt 遵守は**必要条件の一部**にすぎない。①軽微性（本文抽出は軽微性を自ら壊す）
   ②著作権者の利益を不当に害しないこと ③**利用規約という契約**（著作権法とは独立に拘束する）を代替しない。
   ゼクシィ / リクルート系の規約が自動収集・転載を禁じている可能性は高く、これは要確認事項である。
   （法令解釈は法的助言ではない。実際に踏み込むなら専門家確認の対象。）

4. **運用上の失敗モードが既知。**
   はてブと Ameblo は「取得できない」ではなく**「内容不一致」**で無効化した（§1）。
   HTML スクレイパの典型的な壊れ方も同じ「静かに間違った内容を返す」であり、
   しかも `scripts/check-sources.mjs` は週次・PR CI 非対象のため**検知が最大7日遅れる**。
   その壊れ方を、法的リスクの最も高い経路で増やすことになる。

**唯一許容しうる代替**は、本文を一切読まない **sitemap.xml + OGP / JSON-LD カードアダプタ**。
OGP は第三者がカードを描画するために媒体が置いているメタデータであり、本文抽出とは行為の性質が異なる。
`og:title` / `og:description` / `og:image` と JSON-LD の `author` / `datePublished` **のみ**を読み、
`hasSourceText=false` を固定する。ただし規約クリアが前提で、優先度は最下位（§5 V2）。

### 4.2 統計・公的データは `posts` テーブルに入れない

`PostUpsertInput`（`src/lib/db/repository.ts:11-27`）と ingest パイプラインは
「継続的に流入し、新しさで並び、`CURATION_BUDGET=40` で選抜される記事」を前提にしている。
統計はこの前提をどれも満たさない。

- **更新頻度**: 年1回。アダプタ + `SOURCE_REGISTRY` 登録 + `check-sources.mjs` の監視対象を、年 1〜3 行のために作ることになる。
  さらに1年間 yield 0 が続くため、死活監視が常時「怪しい」状態になる。
- **スコアリング不適合**: `usefulness.ts` のゲートは `ceremonyDecision && !preDecisionOrPhotoShoot`。
  婚姻件数統計は「式を決めた読者の意思決定に効く」情報ではない。
- **厚労省 `news.rdf` は規約により不可**（§2.2）。技術的に取れることと採ってよいことは別。

**妥当な表現は静的リファレンス。** 費用相場等を出したいなら、
定数 + 出典名 + 調査年 + 出典元への直リンクを**年1回人手で更新**する。
数値そのものは事実であって著作物ではないため、
`平均費用 X 万円（出典: ゼクシィ結婚トレンド調査 2025）` の形の引用は安全。
**PDF を LLM に要約させることは §10 の観点で不可。**

> 判断の目印: 統計について「自動更新したい」という要求が出た時点で、それは不採用のシグナルである。

### 4.3 `author` が null であることは不採用理由にならない — が、現行 UI には別の問題がある

著作権法 48 条の出所明示は、著作者名が明示されていない著作物について著作者名を要求しない。
企業メディアの署名なし記事の出所は**媒体名**であり、`sourceName` は常に存在する。
よって「author が取れないソースは採らない」は、**形式論で最良の国内ソースを落とす誤った基準**である。

問題は別にある。**`author` 非 null 時のみ表示する現行実装では、`author` が null のカードでクレジット欄が空になる。**
これは §10 が本当に防ぎたいもの（自社コンテンツに見える／ゼロクリック感）に直撃する。

対応（新規ソース追加より先にやる価値がある）:

- `sourceName`（媒体名）を**常時必須のクレジット枠**に昇格させ、`author` はその追加行にする。条件分岐を逆にする。
- **確認済み（V0-2 実測・2026-08-23）**: `sourceName` は RSS `<source>` 由来の実出版社名で正しく、**§10-2 欠陥なし**。
  `canonicalizeUrl` は `news.google.com` のリダイレクトを媒体直 URL に解決しないが、サーバー側解決は
  そもそも不可能（§5 V0-2 追試）。**§10-1 については news.google.com リダイレクトを現状許容**と決定
  （batchexecute 等の非公開 API 依存は採用せず）。詳細は V0-2 追試の「決定」を参照。

## 5. 検証プランと却下ゲート

この誤読が起きやすいため、ゲートは順序付きで評価し、**G1 を必ず最初に置く**。

#### V0-2 追試: リダイレクト解決の可否（サーバー側 fetch プローブ実測）

`news.google.com/rss/articles/...` に対しサーバー側から `fetch(redirect: 'follow')` を実行した結果:

- HTTP 302 は返らず **200 + JS インタースティシャル（約 580KB の HTML）**。最終 URL は `news.google.com` のまま
- User-Agent をブラウザ相当に変えても挙動は同一
- 結論: **HTTP リダイレクト追従による媒体直 URL の解決は不可能**

リダイレクト解決を実装したが、効果ゼロかつ全アイテムで無駄通信（580KB/件）になるため**差し戻し済み**。
残る解決路は Google 内部 API（batchexecute）への依存のみだが、非公開エンドポイントの直接利用は
脆弱性（Google 側変更で即死）・法務（利用規約）両面の懸念があり**保留（ユーザー判断事項）**とする。
当面の緩和策は V1 による Google News 依存度そのものの低減。§6-5 のクエリ拡張はこの保留を前提に再評価する。

**決定（2026-08-23・ユーザー承認）**: §10-1 の news.google.com リダイレクトを**現状許容**する。

- 理由: サーバー側解決は不可能（200 + JS インタースティシャル）。batchexecute 等の非公開 API 直接利用は
  脆弱性（Google 側変更で即死）・利用規約の両面で採用しない。
- 影響: カードのリンクは Google 経由のリダイレクト先となるが、ブラウザで開けば元記事へ到達するため dead link ではない。
  ただし §10-1「主動線を元ソースへ」の理想からは一段下がる制限として本計画に明記する。
- これに伴い **§6-5 の Google News クエリ拡張は見送り**（Google News 依存を低減する方針と整合）。

### V1 — note タグ拡張（推定 1h・最小コスト・唯一の低リスク拡張）

既存アダプタ・既存の法的前提・author ありをそのまま流用できるため、ソース拡張をやるならここが最初。

1. 候補タグを 10 件挙げ、既存 `fetch` でドライラン実行（DB 投入はしない）
2. タグごとに測定 — 取得件数 / `ceremonyDecision && !preDecisionOrPhotoShoot` 通過率 / 既存 URL との重複率

**却下ゲート**: 通過率の下限と重複率の上限を**着手前に数値で確定**し、それを満たさないタグは登録しない。
「一応入れておく」を明示的に禁止する（`HATENA_BOOKMARK_TAGS` / `AMEBLO_BLOG_IDS` を無効化した経緯の再発防止）。

確定した閾値（2026-08-23、V0-3 の実測ベースで着手前に固定）:

| ゲート         | 閾値                                                     | 根拠                                                                                    |
| -------------- | -------------------------------------------------------- | --------------------------------------------------------------------------------------- |
| G-V1a 取得件数 | 候補タグあたり直近30日で **≥ 3 件**                      | 既存 7 タグの平均は約 3.3 件/月（23件/30日）。それ未満は yield 監視を常時警報させるだけ |
| G-V1b 通過率   | `ceremonyDecision && !preDecisionOrPhotoShoot` **≥ 40%** | 体験談・日記・店舗販促が混在するタグは内容不一致（はてブ/Ameblo の失敗の再演）          |
| G-V1c 重複率   | 既存登録タグとの URL 重複 **≤ 50%**                      | 重複が過半なら新規性がなく `CURATION_BUDGET` を消費するだけ                             |

ドライランで 3 ゲートすべてを満たしたタグのみ `NOTE_HASHTAGS` に追加する。

### V1 実測結果（2026-08-23）

#### 手法

既存アダプタ `fetchNote` と同一の `parseFeed` を呼び、得られた `{title, excerpt}` を本番と同じ `curatePosts`（prompt v4 / gemini-3.1-flash-lite / temp 0）で評価。DB 書き込みなし。
測定スクリプト: `scripts/v1-note-dryrun.mjs`（候補10タグ）/ `scripts/v1-control-group.mjs`（既存7タグ）/ `scripts/gate-dist.mjs`（本番分布）。

#### 本番分布（読み取りのみ・43件）

| ソース          | 総数 | ゲート通過 (ceremonyDecision && !preDecisionOrPhotoShoot) | 通過率 |
| --------------- | ---- | --------------------------------------------------------- | ------ |
| 全体            | 43   | 8                                                         | 18.6%  |
| Google ニュース | 20   | 5                                                         | 25.0%  |
| note            | 23   | 3                                                         | 13.0%  |

#### 拡大ドライラン（各タグ直近30日最大25件を評価）

- 対照群（既存7タグ）: 評価 164 件 / 通過 0 件 / **0.0%**
- 候補群（10タグ）: 評価 50 件 / 通過 0 件 / **0.0%**

#### 矛盾の解消（入力忠実度の検証）

本番分布 13% とドライラン 0% の食い違いについて、`note.ts` → `parseFeed`（`feed-parser.ts`）の抜粋生成経路を確認。
ドライランも本番も同一の `parseFeed`（`content:encoded` 優先 → `stripHtml` → `EXCERPT_MAX_CHARS=600` で切り詰め）を通り、同じ `{title, excerpt}` を `curatePosts` に渡す。
**入力は同一**であるため、食い違いは「入力の劣化」ではなく**アイテム集合の違い（歴史的取得物 vs 直近フィード）＝コンテンツ／時期ドリフト**によるもの。

#### ゲートの再評価と結論

- 初期閾値 G-V1b≥40% は、実測ベースライン（既存 note 13%・Google News 25%・直近フィード 0%）を大幅に上回り**誤キャリブレーション**と判明。いかなるタグも満たせず、ゲートとして機能しない。
- ゲートはフィルタではなく**ソートシグナル**（落選投稿も低スコアでレーンに入る、ボーナス 12 vs 0）。したがって「通過率」より「ゲート通過アイテムの絶対供給数」がレーン品質に効く。
- 直近フィードの通過率が全タグで ~0% なので、通過率ベースのゲートは退化（全タグ 0% で同着）。非退化な信号は「期間あたりのゲート通過貢献数」だが、これも全タグで ~0。
- **結論: 候補10タグはいずれも登録しない（V1 却下）**。理由: 現在のフィードではゲート通過供給を増やせず、追加は `CURATION_BUDGET` を消費する低ランク filler を増やすだけ。`HATENA_BOOKMARK_TAGS` / `AMEBLO_BLOG_IDS` を無効化した経緯と同旨（「一応入れておく」の禁止）。`NOTE_HASHTAGS` は現状維持。

#### 戦略的所見

定番レーンのゲート通過供給は構造的に薄い（全プロダクションで約8件、かつ大半が歴史的取得物）。直近の ingest は新規ゲート通過をほぼ生まない。これは §3 のテーゼ「新着順フィードは定番を出せない」を実測で裏付ける。レーン質の真のレバーは「タグを増やす」ではなく、(a) ゲート利得の向上（プロンプト／抜粋）または (b) レーン名／母集団の是正（§3）である。

### V2 — OGP/sitemap 方式の新規メディア（V0・V1 を尽くしてから）

**サイト単位の逐次ゲート。1つでも落ちたらそのサイトは不採用。**

| ゲート | 内容                                                                                                                                                                   |
| ------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **G1** | 利用規約に自動収集・転載を禁じる条項が**ないことを条文で確認**。「見つからなかった」は**不合格**。条項の有無を明示的に記録する                                         |
| **G2** | robots.txt が対象パスを許可し、Crawl-Delay を実装として遵守できる（ウエディングパークの 60s は実質不採用）                                                             |
| **G3** | sitemap.xml か公開インデックスで更新記事を機械発見できる。**HTML 一覧ページの DOM 解析が必要なら不採用**                                                               |
| **G4** | 記事ページに OGP/JSON-LD が揃っている（title / description / image / datePublished）                                                                                   |
| **G5** | **本文 DOM を一切読まずに実装が完結する。** 読む必要が出た時点で不採用                                                                                                 |
| **G6** | `hasSourceText=false` 固定で AI 要約が生成されないことをテストで固定。**そのテストを意図的に壊して実際に落ちることを確認するまで完了としない**（AGENTS.md 検証ルール） |
| **G7** | 30日運用で `og:description` 欠落率を測定し、人手20件目視での内容不一致率 0。**不一致が出たら即ロールバック**                                                           |

現時点の候補優先順（§2.1 の実測より）: みんなのウェディング（更新頻度・内容適性が最良）→ マイナビウエディング（author あり）。
ゼクシィは G1 の通過見込みが低い。ウエディングパークは G2 で落とす。

### V3 — 統計・公的データ

- 厚労省 `news.rdf` は規約により**却下済み**。再検討しない。
- e-Stat / ブライダル総研 / 法務省は `posts` に入れない（§4.2）。
- UI に出すなら静的定数 + 出典名 + 調査年 + 直リンク、**AI 要約なし**、年1回人手更新。

## 7. 意図的に採用しないもの

- **本文 HTML スクレイピング型アダプタ** — §4.1。ゼロクリック化を最も直接的に進める変更であり、`hasSourceText` ゲートの前提を反転させる
- **厚労省 `news.rdf` の取り込み** — 利用規約が RSS を元にしたサイト作成・再配信を禁止（実測確認済み）
- **ウエディングパーク** — robots.txt で ClaudeBot を名指しで Crawl-Delay 60。禁止ではないが意思表示として尊重する
- **The Knot / Brides 等の海外メディア** — 日本の慣習と乖離し、転用で誤情報化する
- **統計データの `posts` テーブルへの投入** — §4.2。年1回更新はフィードのデータモデルに構造的に適合しない
- **統計 PDF の LLM 要約** — §10-3 に抵触
- **「author が取れないソースは採用しない」という基準** — §4.3。形式論で最良の国内ソースを落とす
- **ソース追加を V0 より先に行うこと** — §3。母集団が直近 ingest なら、ソースを足しても定番性は改善しない
- **`check-sources.mjs` を PR CI に入れること** — AGENTS.md の方針どおり週次のまま
