## 1. なぜこれをやるか

plan 04 の再検証で**ゲートを通過した記事群（本群 6/6）は、大手ウェディングメディアではなく個人ブログ中心**だった。
Stage 1 の実 fetch 調査（§3）で、**その個人ブログ4件は全て WordPress で RSS を持っている**ことが判明した。

したがって必要なのは新しい取得機構ではなく、**既存の RSS パイプラインへのソース追加**である。

これは plan 04 §1 の「RSS は新着を届ける。エバーグリーンは定義上新しくない」と矛盾しない。
あの命題が指していたのは**ソースの内容の性質**（note の UGC、Google News の業界ニュースと PR）であって、
**RSS という搬送路**ではなかった。**エバーグリーンを書くブログの RSS は、エバーグリーンな記事を届ける。**

### 非営利・広告なしについての整理（維持する）

**法的助言ではない。** 著作権法で非営利・無償が明文の免除になるのは実質 §38（上演・演奏・上映・口述）だけで、
**複製と公衆送信には及ばない**。§32 の引用も §47条の5 の軽微利用も非営利免除は無く、利用規約は契約なので非営利でも拘束される。
**非営利性が変えるのは適法性ではなく、問題化する確率と、かけるべきプロセスコストの釣り合いである。**

有利な材料として **§30条の4（情報解析、非営利要件なし）** があり、**取得と判定**を支える。
ただし**生成した要約を公衆送信する段階は §30条の4 の外**に出るため、
「取得・判定は §30条の4 寄り、公開する要約は §32 / §47条の5 寄り」という**二層構造**で整理する。

> **非営利という資産は、対外的に観測可能なポリシー（頻度・UA・robots の尊重・要約の長さ・クレジット・導線）を緩めると消費され、
> 観測不能な内部プロセス（証明様式・観測期間・記録フォーマット）を緩めても一切消費されない。**

### 3.6 検索より確実な発掘経路 ── ホスト昇格

そもそも既知の4件は**検索で見つけたものではない**。plan 04 の再検証で
「ゲートを通過した記事」として浮上した URL のホストを後から見たら、たまたま個人ブログだったという経緯である。

ここに、検索より確実な発掘機構がある。

> **ホスト昇格（host promotion）**: 既存経路（note / Google News / 手動投入）から入った記事が
> **有用度ゲートを通過したとき、そのホストにフィードがあるかを調べ、あればソースとして登録する。**

- 検索エンジンの SEO バイアスを迂回できる
- **既にゲートを通過した実績のあるホスト**だけが候補になるため、歩留まりが構造的に高い
- 新しい取得機構を必要としない。`posts` テーブルを集計して `/feed` の有無を確かめるだけ
- 巡回ではないので robots.txt の継続的な遵守義務も発生しない（登録後は通常の RSS 取得になる）

実装は `scripts/` のワンショットスクリプトで足りる（**cron 化しない**）。

```
ゲート通過 posts のホスト別集計 → 未登録ホストを抽出 → 各ホストの /feed 等を1回だけ確認 → 候補として人間に提示
```

**この経路を §7 の実行順に組み込む。** 検索ベースの発掘は、歩留まりが低いことが実測されたため主戦略にしない。

## 4. 【最重要】全文配信フィードは §10 の前提を崩す

### 4.1 実測

`feed-parser.ts:150` は **`content:encoded`（本文全体）を優先し、無ければ `description`** を使う。
候補ブログの実フィードを取得して文字数を測った結果が以下である。

| ホスト                           | `description` 平均 | `content:encoded` 平均 |
| -------------------------------- | ------------------ | ---------------------- |
| `rukamama-note.com`              | 132                | **16,846**             |
| `kizuna-bridal.com`              | 90                 | **12,376**             |
| `www.wedding-note.net`           | 122                | 0（**抜粋配信**）      |
| `soratobu-penguin.com`           | 未取得（§11）      | 未取得                 |
| `engage-ring-fun.com`（新候補）  | 50〜150            | **2,000〜8,000**       |
| `kodawariwedding.club`（新候補） | 50〜150            | **3,000〜6,000**       |
| （参考）`note.com`               | 322                | **無し**               |

`EXCERPT_MAX_CHARS = 600` なので、現状のまま追加すると **16,846文字の本文の先頭600文字**が `originalExcerpt` になり、
そのまま LLM の要約材料として渡る。著者自身が書いた132文字の `description` は**使われない**。

### 4.2 なぜ問題か

plan 03 §4.1 で本文スクレイピングを不採用にした論拠は、
**「RSS の抜粋は媒体が配布を意図した要約であり、本文の創作的表現の切片ではない」**という一点だった。

**全文配信フィードはこの前提を成立させない。** `content:encoded` は媒体の要約ではなく著作物そのものである。
これを 600 文字で切って要約材料にする行為は、**スクレイピングを避けた意味を搬送路の違いだけで失わせる**。

さらに重要な事実として、**既存ソースにこの曝露は無い** ── `note.com` に `content:encoded` は存在せず（実測）、
はてブと Ameblo は無効化中である。**つまり本文全体をパイプラインに取り込むのは、この変更が初めてになる。**

### 4.3 対処: `description` を優先し、`content:encoded` はサムネイル抽出専用にする

`feed-parser.ts` の `bodyHtml` は2つの用途に使われている（L150, L156, L162）。**これを分離する。**

| 用途                                     | 現状                             | 変更後                                                              |
| ---------------------------------------- | -------------------------------- | ------------------------------------------------------------------- |
| `excerpt`（要約材料）                    | `content:encoded ?? description` | **`description ?? content:encoded`**                                |
| `thumbnailUrl`（本文中の最初の `<img>`） | `content:encoded ?? description` | **変更なし**（サムネイル URL の抽出は創作的表現の利用にあたらない） |

`description` が空のフィードでは従来どおり `content:encoded` にフォールバックするため、**テキストが取れなくなる退行は起きない**。
既存ソースへの影響も無い（note は `content:encoded` を持たず、Google News も `description` のみ）。

> **これは緩和ではなく強化である。** 著者自身の要約を使うほうが、§10-3（創作的表現を再現しない）にも近い。

## 5. アフィリエイトは入口で弾かない（判定で下げる）

### 5.1 既存の `promotional` 判定が既に機能している

当初は「アフィリエイトサイトを採用前に人間が確認して除外する」ことをブロッカーに置いていたが、**これは過剰だった**。
キュレーション判定には既に `promotional` があり、スコアを下げる仕組みが動いている。

| 事実                                                                              | 位置                                              |
| --------------------------------------------------------------------------------- | ------------------------------------------------- |
| `USEFULNESS_WEIGHT_PROMOTIONAL_PENALTY = 4`                                       | `src/lib/constants.ts:169`                        |
| **他の加点項（firsthand / specific / tradeoff）より意図的に大きく**設定されている | `src/lib/scoring/usefulness.ts:91`                |
| `GATE_BONUS - PROMOTIONAL_PENALTY` が加点合計を上回る不変条件が明記されている     | `src/lib/constants.ts:147`、`usefulness.ts:66-67` |
| 判定基準は**「読者が別の会場・別の業者で式を挙げる場合にも役立つか」**            | `src/lib/llm/prompts.ts:44`                       |

プロンプトの定義は「事業者による集客・自社サービスへの誘導が主目的なら true。職能者による記事でも、
特定の自社サービス・自社会場・特定商品への誘導が主眼なら true」であり、**アフィリエイト誘導型の記事はここで捕捉される**。

**したがって、アフィリエイトの有無を採用可否の入口条件にしない。入れても順位が下がる。**

### 5.2 それでも入口で見るもの（軽量チェック・1〜2記事の目視）

記事単位の減点では追いつかず、**ソース全体が低品質な在庫を大量に持ち込む**ケースだけを弾く。

- **体験の実体が無く、アフィリエイト誘導だけで構成されたサイト**
- **結婚式が主題でないサイト** — 生活雑記・投資・グルメ等が中心で、結婚式は一カテゴリに過ぎない（§3.6 に実例）
- **業界解説型** — 自分の結婚式の意思決定ではなく業界インサイダーの一般論（plan 04 §1.5 の「誰が書いても同じ表面的な内容」に近い）
- **更新が数年前で停止しているサイト** — flow が期待できない。ただし在庫の質が高ければ §6.4 の手動投入の対象にはなる

### 5.3 個人ブログを扱うことの含意

対象が大手企業ではなく**個人の書き手**である以上、クレジットの正確さと導線の明示は、法務要件である以上に礼儀の問題になる。
WordPress ブログは `dc:creator` が取れるので §10-2 を満たせるが、
**はてなブログのフィードには author が無い**（§3.6 で実測）。
その場合 `sourceName`（ブログ名）が唯一のクレジットになるため、**§10-2 の観点で `sourceName` の正確さがより重要になる**。

## 6. 実装計画

### 6.0 変更が不要なもの（確認済み）

- **`dc:creator` の読み取り** — `feed-parser.ts:151` が `readAuthor(item["dc:creator"], ...)` で既に対応済み。**パーサの著者処理に変更は要らない**
- **RSS 2.0 のパース** — 既存の `parseFeed` で足りる
- **重複排除** — `canonicalizeUrl` + `posts.url` unique + ingest の Set 重複排除で足りる

### 6.1 P1: `feed-parser` の excerpt ソース分離（§4.3・**最優先**）

`parseRss2Item` / `parseAtomEntry` で、要約材料とサムネイル材料を分ける。

- `excerptHtml = description ?? content:encoded`
- `thumbnailHtml = content:encoded ?? description`（現状の `bodyHtml` 相当）
- `excerpt: truncateExcerpt(excerptHtml)` / `resolveRss2Thumbnail(item, thumbnailHtml)`

**テストで固定する**（AGENTS.md「意図的に壊して落ちることを確認するまで完了と見なさない」）:

| #   | 固定する不変条件                                                                                         |
| --- | -------------------------------------------------------------------------------------------------------- |
| T1  | `description` と `content:encoded` の両方があるとき、`excerpt` は `description` 由来になる               |
| T2  | `description` が空で `content:encoded` のみのとき、`excerpt` は `content:encoded` 由来になる（退行なし） |
| T3  | `content:encoded` にのみ `<img>` があるとき、`thumbnailUrl` は従来どおり取得できる                       |
| T4  | 既存の note フィード形式（`content:encoded` なし）で挙動が変わらない                                     |

### 6.2 P2: WordPress ブログアダプタの実装

`src/lib/sources/ameblo.ts` が最も近い先例（個別ブログ RSS を ID リストで巡回する形）。ただし**決定的な違いが1つある**。

> Ameblo は `sourceName` が「アメーバブログ」というプラットフォーム名で足りるが、
> **本件は1ブログ＝1つの媒体であり、`sourceName` はブログ自身の名前でなければならない**（§10-2）。

したがってアイテムに出自を持たせる必要がある。

```typescript
// src/lib/sources/wordpress.ts（新規）
export type WordPressItem = FeedEntry & {
  blogId: string;
  blogDisplayName: string; // toPost で sourceName に使う
};
```

- 1ブログあたりの取得件数は Ameblo と同様に少なめ（更新頻度が低いため）
- 1ブログの失敗は他をブロックしない（`fetchRssText` が null を返したら空配列、既存パターン）
- ブログ間は `Promise.all` で並列（`Crawl-delay` の記載が無いため）

### 6.3 P3: 定数・レジストリ・監視の登録

| 対象                          | 作業                                                                                                                         |
| ----------------------------- | ---------------------------------------------------------------------------------------------------------------------------- |
| `src/lib/constants.ts`        | `WORDPRESS_BLOGS`（`{ id, displayName, feedUrl, disabledReason? }` の配列）。`check-sources.mjs` の `targets` と同じ形にする |
| `src/lib/sources/registry.ts` | `SOURCE_REGISTRY` に `wordpress` を追加。`toPost` で `sourceName: item.blogDisplayName`、`author: item.author`               |
| `scripts/check-sources.mjs`   | `targets` に各ブログの feed URL を追加（週次死活監視）                                                                       |

**`sourceId` は `"wordpress"` 単一**とし、媒体の区別は `sourceName` で行う。
`SOURCE_REGISTRY` のキーが `sourceId` になる既存設計に従う。

### 6.4 P4: 在庫（stock）の投入

RSS が届けるのは**新着（flow）だけ**であり、既存の在庫 200件強は流れてこない。
これは**既存の手動 CLI で投入する**（新規実装は不要）。

```
post-sitemap.xml から URL リストを生成 → submit-evergreen.mjs --file
```

- **一度に全件を投げない。** `submit-evergreen.mjs` は URL 間 4秒 sleep なので、200件で約14分。相手サーバへの配慮として分割する
- 投入結果を人間がレビューし、§1.5 のトピック判定が効いているか確認する
- `sitemap` は「巡回対象」ではなく**一度きりの URL リスト生成元**として使う。`discovery_seen` のような状態管理は要らない

### 6.5 P5: spec.md の更新

- §6.3（収集ソースの採否）に WordPress ブログ経路を追記
- §10-3 の担保として §4.3 の「著者自身の `description` を優先する」方針を記載
- 4件のブログの採否と、その根拠（§5.1 の確認結果）を記録

### 6.6 P6: ホスト昇格スクリプト（§3.6）

`scripts/` にワンショットスクリプトを追加する。**cron 化しない。**

- `posts` と `post_usefulness_criteria` を結合し、**ゲート（`ceremonyDecision && !preDecisionOrPhotoShoot`）を通過した投稿のホスト別件数**を集計
- `SOURCE_REGISTRY` と `WORDPRESS_BLOGS` に未登録のホストを抽出
- 各ホストについて `/feed`, `/feed/`, `/rss`, `/atom.xml` と `<link rel="alternate">` を**1回だけ**確認
- フィードが見つかったホストを、`dc:creator` の有無・`description`/`content:encoded` の文字数とあわせて**人間に提示**する

登録の可否は人間が決める。スクリプトは候補を並べるだけで、自動登録はしない。
