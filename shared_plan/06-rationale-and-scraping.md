## 1. 結論

**出力を「要約」から「判定根拠」に変えたうえで、本文取得による収集を実施する。**

順序は交渉不可である。**出力の転換が前提条件であり、それ無しに本文取得だけを始めてはならない。**
本文が取れる状態で出力が要約のままだと、plan 03 §4.1 が警戒した状態（本文が要約材料になる）に戻り、
ゼロクリック化のリスクだけが増える。

| 決定    | 内容                                                                                                        |
| ------- | ----------------------------------------------------------------------------------------------------------- |
| 出力    | AI 要約を廃止し、**判定根拠（トピック行＋基準チップ）**に置き換える。タイトルは**元記事タイトルの逐語表示** |
| 取得    | **セクション単位**で対象を選び、sitemap の差分から本文を取得して判定する                                    |
| 保存    | **本文は永続保存しない。** 判定後に破棄し、URL・元タイトル・著者・日付・サムネイル・判定結果のみを残す      |
| 第1対象 | `mwed.jp` の体験談セクション（`sitemap_stories.xml`、423件、**実測ゲート通過率 50%**）                      |

## 2. 前提: 出力を判定根拠に変える

### 2.1 二層構造が「例外依拠」から「射程外」になる

**以下はいずれも法的助言ではない。日本法を前提とした技術設計上の整理である。**

| 層         | 行為                                   | 依拠                                                 |
| ---------- | -------------------------------------- | ---------------------------------------------------- |
| 取得・判定 | sitemap 巡回、本文取得、LLM による分類 | **§30条の4**（情報解析。非営利要件なし）             |
| 公開       | 判定根拠カードの公衆送信               | **著作権法の射程外**（原著作物の表現を含まないため） |

§30条の4 は「著作物に表現された思想又は感情を自ら享受し又は他人に享受させることを目的としない場合には、
その必要と認められる限度において、**いずれの方法によるかを問わず、利用することができる**」と定め、
第2号で情報解析（「多数の著作物その他の大量の情報から、当該情報を構成する言語…に係る情報を抽出し、比較、分類その他の解析を行うこと」）を明示列挙している。

要約を出力する現行設計では、公開層が §32 引用 / §47条の5 軽微利用という**例外規定に依拠**していた。
出力に原著作物の表現が含まれなくなると、公開層は**そもそも著作権法の射程外**になる。
**例外規定（争われうる）に依拠する立場から、保護対象が存在しないという立場への移行**であり、質的な改善である。

**ただし3つの留保**:

1. **§32 の引用という正当な経路を自ら放棄する**ことになる。その自覚を持つこと
2. **残余リスクは著作権から民法709条に移る**（§3.2 のヨミウリ）
3. **論評という新しいリスク軸が増える。** 根拠文は第三者の著作物への**評価**である

   緩和策（**現行の掲載ロジックがそのまま防御になっている。維持すること**）:
   - **採用した記事の根拠文しか出さない**
   - **否定的評価は一切公開しない**（スコア非公開＝spec.md §9.8 と整合）
   - **記述的トーンに徹する**

### 2.2 根拠文の設計制約

> **根拠文は「記事の性質についての言明」であって、「記事の内容の配達」であってはならない。**

**判定テスト: 読者がクリックせずに情報要求を満たせるなら、代替物を作ってしまっている。**

| 項目           | 制約                                                                                                     |
| -------------- | -------------------------------------------------------------------------------------------------------- |
| 長さ           | **60〜90字**（現行要約は100〜150字。意図的に短く）                                                       |
| 数値           | **記事固有の具体数値は一切禁止。** 「総額430万円」はペイロード、「総額の内訳を実額で開示している」が性質 |
| 表示可能なメタ | 自前で構造化して持っている軸のみ。**金額・式場名・商品名・日付・個別の出来事の描写は不可**               |
| 事実の粒度     | **記事固有のアンカーは最大1つ。かつトピックのアンカーであって、結論のアンカーであってはならない**        |

- **可**: 「持ち込み料の交渉について書いている」（トピック → クリックさせる）
- **不可**: 「持ち込み料3万円が交渉で免除された」（結論 → クリックを代替する）

**事実の大量抽出について**: 個々の事実は著作物ではないが、(a) 網羅的・体系的な抽出は編集著作物／不法行為の線に近づき、
(b) 事実の**選択と配列**が原文をなぞれば選択配列の創作性を通じて翻案側に戻る。
よって **「カードあたり事実1つ」「原文の順序を再現しない」** を制約に含める。
**テンプレート性はここでは欠点ではなく美点である。** 自由記述は要約への drift を招く。

**chips-first で設計する。** 6つの boolean は既に存在し、**ラベル付き chip として描画するだけで価値の9割をリスク0%で得られる。**
自由文はその上の限界的な追加であり、「トピックアンカー1行」に切り詰める。

### 2.3 `aiTitle` は元記事タイトルの逐語表示に変える

**これは本検討で最も重要な発見である。現行カードで最もリスクが高いのは `aiSummary` ではなく `aiTitle` だった。**

| 観点                    | 内容                                                                                                                                |
| ----------------------- | ----------------------------------------------------------------------------------------------------------------------------------- |
| 著作物性                | タイトルは短く著作物性が否定されやすい（ヨミウリ見出し事件）。**逐語表示はリスクが低いほうの選択肢**                                |
| **同一性保持権（§20）** | **人格権であり非営利免除は無い。** 他人の記事タイトルを AI で30字に書き換えて表示する行為は、本システム全体で**改変にいちばん近い** |
| 分岐の帰結              | 元タイトルに著作物性が**あれば**書き換えは翻案＋同一性保持権侵害。**無ければ**逐語表示は完全に自由。**両方の分岐で逐語が優越する**  |
| 業界慣行                | 検索結果・RSS リーダー・SNS カードは全て元タイトルを出す。**逸脱するほうが異例**                                                    |

UX 懸念（煽り・冗長）への対処は**書き換えではなく `line-clamp` と省略**。
煽りタイトルの隣に冷静な性質行が並ぶのはむしろ良く読める ── 編集的な声のコントラストになる。

### 2.4 カード構成

```
元記事タイトル（逐語・line-clamp）
神前式・持ち込み交渉について              ← トピックアンカー ≤40字
[当事者本人] [実費の内訳] [トレードオフ]   ← 既存の 6 boolean
ソース名 / 著者名                    → 元記事へのリンク（最優先 CTA）
```

**製品リスクは「要約が無いこと」ではなく「カード間の差が無いこと」である。**
6 boolean ＋テンプレート文だけだと30枚が同じ文面になり、読者の次の意思決定に何も与えない。**単調さで死ぬ。**
トピックアンカーはこの緩和策であり、**必須**とする。

## 3. 判断の根拠

### 3.1 技術的な障害は存在しない（実測・2026-08-24）

| ------------------- | ---- | ------------------- | ------------ | ------- |
| `zexy.net`          | 200  | Apache              | 3,038字      | なし    |
| `www.mwed.jp`       | 200  | nginx + CloudFront  | **20,415字** | なし    |

WAF ブロックも JS レンダリング依存も無い。

### 3.2 障害の 4/5 は「スクレイピングだから」ではなく「出力方法」の問題だった

| 障害                      | 実際に何を禁じているか                                                                            | スクレイピング固有か   |
| ------------------------- | ------------------------------------------------------------------------------------------------- | ---------------------- |
| **民法709条（ヨミウリ）** | 違法とされたのは「営利目的で反復継続して、無断で、**デッドコピーし、約2万サイトに配信**」した行為 | **否。出力の問題**     |
| **著作権（§30条の4）**    | 情報解析目的の利用を原則許容。**入力側はカバーされる**                                            | **否**（最も弱い障害） |
| **利用規約**              | 5社とも禁じているのは**複製・転載・利用**。**クローラを名指しした条項はゼロ**                     | **否。出力の問題**     |
| **§47条の5 の政令要件**   | 所在検索サービスの免責要件。**この条文に依拠しないなら拘束しない**                                | **否**                 |

**5社ともアクセス方法を縛る条項は無く、縛っているのはコンテンツの利用である。**
根拠文方式（複製せず、自分の表現で性質を述べる）はその射程に入りにくい。

**留保**: マイナビの「私的利用の範囲を超えて使用」とハナユメの「あらゆる方法において利用または使用」は文言が広く、

### 3.4 唯一スクレイピング固有の障害 ── 業務妨害

**岡崎市立中央図書館事件（Librahack、2010年）**:

- 偽計業務妨害容疑で **2010-05-25 逮捕、約20日間勾留**
- アクセスは**1秒に1回程度**のシリアルアクセス
- 図書館側の旧システムに「**1時間400リクエスト以上で他のリクエスト処理が不能になる不具合**」があった
- 産総研等の解析で「クローラに違法性はなく、図書館システム側の不具合」と判定
- **2010-06-14 起訴猶予**（有罪認定なし）

**技術的に穏当な頻度でも刑事手続の対象になり得た国内の実例である。**
一方でこれは**アクセス量の問題**であり、§5.4 の規律で管理できる性質のものである。

### 3.5 効用は実測により裏付けられた

初版は「大手メディアはゲートを通らない」と述べたが、根拠は**式場探し系4件の対照群だけ**で、
**体験談セクションは一度も測っていなかった**。

`mwed.jp` の `sitemap_stories.xml`（423件）から無作為抽出した8件の実測結果:

| 母集団                                       | ゲート通過率     |
| -------------------------------------------- | ---------------- |
| 既存 RSS パイプライン（note + Google News）  | 8/43 = **18.6%** |
| 対照群（式場探し系の商業メディア記事）       | 0/4 = **0%**     |
| **`mwed.jp` 体験談セクション（無作為抽出）** | **4/8 = 50.0%**  |

- **8件すべてが `firsthand=true` かつ `specific=true`**
- 落ちた4件は**すべてフォトウェディング**（`preDecisionOrPhotoShoot=true`）。判定項目が意図どおり分離している
- 通過4件のうち2件は `promotional=true` だが、減点4を受けてなおゲートを通過

**無作為抽出で 50% は、これまで測定したどのソースより高い。**

### 3.6 残る本当の制約は3つ

1. **アクセス量の規律**（§5.4）── レート制限・件数上限・条件付き GET・robots.txt の尊重
2. **文言の広い規約への留保**（§4.3）── マイナビ・ハナユメ
3. **静かに壊れる失敗モード**（plan 03 §4.1(d)）── DOM 変更で無言の誤取得。**法務ではなく工学の問題**（§9 の `G-yield` で捕捉）

## 4. 対象の選定 ── サイトではなくセクション

### 4.1 セクション単位で見る

**大手メディアは異質なセクションの集合体である。** コラム（式場探し）は落ちるが体験談は通る。
初版の「大手は使えない」は**サイト単位の過度な一般化**だった。

**したがって対象は「サイト」ではなく「sitemap のセクション＋パス接頭辞」で定義する。**

### 4.2 第1対象: `mwed.jp` 体験談

| 項目             | 内容                                                                                                             |
| ---------------- | ---------------------------------------------------------------------------------------------------------------- |
| 発見元           | `https://www.mwed.jp/sitemap_stories.xml`（**423件**、`lastmod` は 2023-09〜2025-04 で分散）                     |
| パス接頭辞       | `/story/cases/`、`/hall/*/rev/story/`                                                                            |
| robots.txt       | 一般 UA への明示ブロック無し、AI クローラの名指し無し、`Sitemap:` 記載あり                                       |
| 実測ゲート通過率 | **4/8 = 50.0%**                                                                                                  |
| OGP              | **無し**（plan 05 §3.3）。だから本文取得が必要であり、逆に言えば**本文取得なしには扱えない唯一の高収率ソース**   |
| ToS 留保         | 「無断転載・無断利用禁止」＋収益補填請求権。**アクセス制限条項は無い**。根拠文方式なら転載・利用にあたらない整理 |

**まずここ1つだけで開始する。** 他サイトへの展開は §9 の kill gate を30日通過してから。

### 4.3 留保付き ── マイナビ・ハナユメ

**規約の文言が広いため、第1段階では対象にしない。** 進めるなら**許諾を取りに行く**（§13）。
5社とも問い合わせ窓口があり、マイナビは編集部直通 `m-wed-edit@mynavi.jp` を公開している。
**非営利・広告なし・出典明示・送客のみという条件は、媒体側にマーケティング上の合理性があり、通る可能性がある。**

### 4.4 除外 ── ウエディングパーク

robots.txt で **ClaudeBot / GPTBot / bingbot を名指しで `Crawl-Delay: 60`**、
ToS も5社中唯一「**事前の書面による承諾**」を明示。**対象にしない。** 必要なら許諾で解く。

## 5. 取得の設計

### 5.1 発見 ── sitemap の差分

plan 05 §7.1 の設計をそのまま採用する。

- **正しさの根拠は「既知 URL 集合」であって `lastmod` ではない。** sitemap に載っていて既知集合に無い URL を新規とみなす
- **`lastmod` は最適化としてのみ使う**（どの子 sitemap を読むか絞る）。取りこぼしても次回に回収される
- `lastmod` の病理（全件同一時刻・未来日付・TZ 欠落）に備え、**1回の差分件数が閾値を超えたらその媒体の `lastmod` を信用しない**
- **「新規 URL」と「既知 URL の更新」を分け、後者は原則無視**（誤字修正や広告差し替えで更新される）
- **初回バックフィルは行わない。** sitemap 上の URL を全部「既知」として記録するが**取得はしない**（seeding のみ）。
  在庫は既存の手動 CLI で段階投入する
- sitemap は既存の `fast-xml-parser`（`feed-parser.ts` が使用）で**新規依存なしにパースできる**

### 5.2 本文取得と抽出

- 新規モジュール `src/lib/sources/article-text.ts`
- `script` / `style` / `noscript` を除去してからタグを落とし、可視テキストを得る
- **取得サイズの上限**（例: 512KB）を設け、超過は打ち切る
- **判定に渡すのは先頭ナビ部をスキップした一定量**（測定では 1,200字スキップ後の 1,500字で 50% を得た）
- 抽出失敗（テキスト量が閾値未満）は `evidenceSufficient=false` として `pending` 保存（§7 P5）

### 5.3 【最重要】本文を永続保存しない

> **判定後に本文を破棄し、`posts` には URL・元タイトル・著者・公開日・サムネイル URL・判定結果のみを残す。**

理由は3つ。

1. **§2.1 の二層構造を維持できる。** 「解析のために取得し、解析後は保持しない」という形は §30条の4 の趣旨に沿う
2. **「他人の著作物のデータベース」を作らない。** 永続保存はそれ自体が新たな露出になる
3. **将来の drift を構造的に防ぐ。** 本文が DB にあると、いずれ誰かが要約に使う。**無ければ使えない**

`originalExcerpt` には**本文を入れない**。根拠文の生成元は `post_rationales` 側に持つ（§6）。

### 5.4 アクセス規律

| 項目                | 規律                                                                                                                               |
| ------------------- | ---------------------------------------------------------------------------------------------------------------------------------- |
| 間隔                | ホストあたり**最低 5 秒**（robots.txt に `Crawl-delay` があればその値を下限として尊重）                                            |
| 並列                | **ホスト内は逐次。ホスト間のみ並列**                                                                                               |
| 総量                | **ホストあたり日次ハードキャップ**（初期値 50 件）。間隔だけ守って総量が青天井なのが、差分巡回が壊れたときの事故形態               |
| 条件付き GET        | `If-Modified-Since` / `ETag` を送る。**304 は相手のコストをほぼゼロにする。礼儀と効率が一致する数少ない箇所**                      |
| User-Agent          | `WeddingTrendBot/1.0 (+https://<本番ドメイン>/about)` ── **連絡先を必ず含める。** 匿名クロールは後から「隠れてやっていた」に見える |
| robots.txt          | 取得前に確認。キャッシュは **24時間以内**（RFC 9309 の推奨）                                                                       |
| 429 / `Retry-After` | **指定値を厳密に守って1回だけ再開。**24時間内に2回目でそのホストを自動無効化                                                       |

**UA 偽装は行わない。** 名乗ったうえで断られるなら従う。これは §2.1 の立場全体の一貫性に関わる。

### 5.5 実行基盤

- **GitHub Actions**（リポジトリは public のため実質無制限、既存 `weekly-monitor.yml` と同じ `ubuntu-latest`）
- **1ジョブ 15〜20分を上限**とし、総量は頻度で稼ぐ。**6時間枠は使わない**（Actions ポリシー上いちばん苦しい形態）
- `concurrency` group を設定し、二重実行による重複取得を防ぐ
- Vercel cron は増やさない。`/api/ingest` への相乗りもしない（認可付き単一エントリに条件分岐を生やさない）
- **cron の遅延・欠落・重複は前提**（Vercel も GitHub Actions も best-effort）。§5.1 の設計なら壊れない
- **60日 inactivity で schedule が自動停止する**点に注意（`discovery_run` の最終実行時刻を週次監視の対象に含める）

`ALTER TABLE` 不可・`CREATE TABLE` 可（`apply-migrations-remote.mjs` が CREATE 系以外を実行拒否）。
**`posts` は無改変**とし、サイドテーブルで拡張する（`post_usefulness_criteria` の慣行に乗る）。

## 9. kill gate

**1つでも観測されたら該当ホストを即停止。回復には人間の再判断を要する。**

| #   | 観測事象                                                  | 扱い                                                                            |
| --- | --------------------------------------------------------- | ------------------------------------------------------------------------------- |
| K1  | robots.txt の内容ハッシュが変化（`G-robots`）             | 該当ホストの discovery を自動停止して再確認。**全ゲート中これが最も価値が高い** |
| K2  | 利用規約に自動収集禁止条項が追加された（`tos_hash` 変化） | 停止して人間が再判断                                                            |
| K3  | 401 / 451 / 403 本文に明示的な文言 / **媒体からの連絡**   | **即恒久停止、自動復帰なし**                                                    |
| K4  | 403（本文取得）                                           | そのホストを即 cool-off 24h ＋通知。**連続2回で恒久無効化**                     |
| K5  | 403（robots.txt / sitemap）                               | K4 より**重く**評価する（配信の意思そのものへの拒否）                           |
| K6  | 429 + `Retry-After`                                       | 指定値を守って1回だけ再開。24時間内に2回目でホスト自動無効化                    |
| K7  | ホストあたり日次リクエストが上限超過（`G-volume`）        | 停止。差分巡回が壊れたときの事故形態                                            |
| K8  | 取得数に対する採用率が閾値未満を継続（`G-yield`）         | 停止。**フィルタか抽出が壊れた合図**（§3.6-3 の捕捉手段）                       |
| K9  | 根拠文が §2.2 の制約に違反（数値混入・結論アンカー）      | **即 revert + 回帰テスト追加**                                                  |
| K10 | 要約と元記事の内容不一致が1件でも出る                     | 停止（plan 03 V2-G7 の 0 件基準を維持）                                         |

**403 を「1回で恒久停止」にしない理由**: GitHub Actions の Azure IP では WAF 起因の 403 が定常的に起きうる。
1回で恒久停止するゲートは数日で「毎回止まる」状態になり、外される。**外されたゲートは無いゲートより悪い。**
