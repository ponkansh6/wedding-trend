## 1. なぜ今これをやるか

前コミットで体験談レーンを有用度順に並べ替えたが、本番43件の実測結果の**上位3件が、いずれも想定読者の状況に合っていない**。

| 順位 | 点  | 中身 | 実体験 | 具体 | 判断 | 宣伝 | タイトル                                 |
| ---- | --- | ---- | ------ | ---- | ---- | ---- | ---------------------------------------- |
| 1    | 17  | ○    | ○      | ○    | ○    | ・   | グランドニッコー東京台場での**フォト婚** |
| 2    | 17  | ○    | ○      | ○    | ○    | ・   | **式場決定前**の見積もり交渉術           |
| 3    | 15  | ○    | ○      | ○    | ・   | ・   | **前撮り**用小道具の毛筆文字             |
| 4    | 15  | ○    | ○      | ○    | ・   | ・   | Canvaを活用した結婚式DIY                 |
| 5    | 15  | ○    | ○      | ○    | ・   | ・   | 結婚式準備で知るBGMの重要性              |

想定読者（spec.md §9.1）は「挙式日・会場が決まっており、衣装もおおむね決まっている」人である。この読者にとって、

- **フォトウェディング / 前撮り**は、そもそも挙式・披露宴とは別のイベントである
- **式場決定前の見積もり交渉**は、既に終わった意思決定の話である

いずれも「もう通り過ぎた」または「そもそも対象外」の話題であり、上位に置くべきではない。記事としての質（実体験・具体的・判断理由あり）が高いために、**質の高さが的外れさを覆い隠して最上位に来てしまっている**のが現状である。

これは重み調整では直らない。`firsthand` / `specific` / `tradeoff` はいずれも正しく true であり、これらの重みを下げれば良質な記事全体が沈む。**足りないのは判定軸そのもの**である。

---

## 2. 根本原因: `ceremonyDecision` の定義が前撮りを吸い込んでいる

現在の定義（`src/lib/llm/prompts.ts:41` および spec.md §9.2）:

> `ceremonyDecision`: 挙式・披露宴の中身の意思決定に効く（進行・タイムライン・演出・席次・席札・余興・スピーチ・BGM・装花・料理・引出物・ペーパーアイテム・**写真映像**・ゲストの過ごしやすさ・当日段取り）。

「写真映像」が**当日の記録（スナップ・エンドロール・記録映像）と、前撮り・フォトウェディングの両方に読める**。LLM は後者も含めて true と判定しており、判定として誤りではない。定義が曖昧なのが原因である。

同様に「式場決定前の見積もり交渉」は、列挙された項目のどれにも該当しないが、「結婚式の意思決定に効く」という広い読みで true になっている。

したがって対応は 2 つ必要になる。

1. `ceremonyDecision` の定義を締める（「写真と映像」を**挙式当日の記録**に限定する）
2. 新しい判定項目を足して、フォトウェディング / 前撮り / 式決定前の話題を明示的に識別する

1 だけでは不十分である。定義を締めても「式場決定前の見積もり交渉」のような、挙式そのものに関わるが読者にとっては終わった話題を落とせない。

## 3. 新しい判定項目の設計

### 3.1 極性が最重要（ここを間違えると良い記事が沈む）

既存の判定方針（spec.md §9.4）に「**判断材料が抜粋に無い場合は false とせよ**」がある。抜粋は記事冒頭しか無いため、この規則は必ず効く。したがって新項目は、**false に倒れたときに無害な側**へ倒れる極性で定義しなければならない。

| 案  | 名前                                                            | 不明時（false）の挙動                                                              | 判定   |
| --- | --------------------------------------------------------------- | ---------------------------------------------------------------------------------- | ------ |
| A   | `postDecision`（式決定後の内容か）                              | false → **減点される**。式決定後の良記事が、抜粋にその旨が書かれていないだけで沈む | ✗ 危険 |
| B   | `preDecisionOrPhotoShoot`（フォト婚・前撮り・式決定前の話題か） | false → **何も起きない**。積極的に識別できたときだけ効く                           | ✓ 採用 |

**採用は B。** 既存の `promotional`（宣伝目的なら true → 減点）と同じ極性であり、既存設計との一貫性もある。「〜であるか」ではなく「〜に限られるか」という**積極的識別**の形にする。

ユーザーの要望文（「式決定後の内容であるか」）とは論理が反転するが、**判定結果として実現される順序は同一**であり、かつ誤判定時の被害が小さい。この反転は意図的なものとして spec.md に理由を残す。

### 3.2 定義文（プロンプトと spec.md で共有する文面）

> `preDecisionOrPhotoShoot`: 内容が次のいずれかに限られる場合に true とする。
> (a) フォトウェディング・前撮り・後撮りなど、挙式・披露宴とは別に行う撮影そのものの話題。
> (b) 式場探し・式場見学・見積もり比較・日取り決定など、**挙式する会場や日程を決めるまで**の段階の話題。
> 挙式当日の写真・映像（スナップ撮影、記録映像、エンドロール）は (a) に**含めない**——これは挙式・披露宴の中身である。
> 式が既に決まっている前提で書かれた記事、あるいはどちらとも判断できない記事は false とすること。

(a) の但し書きが要。これを書かないと「写真」という語だけで当日のスナップ記事まで巻き込む。

### 3.3 スコアへの組み込み: 独立項ではなくゲート修飾子

現在の式（`src/lib/scoring/usefulness.ts`）:

```
score = (ceremonyDecision ? 10 : 0) + 3*firsthand + 2*specific + 2*tradeoff - 4*promotional
```

**変更後:**

```
gate  = (ceremonyDecision && !preDecisionOrPhotoShoot) ? 10 : 0
score = gate + 3*firsthand + 2*specific + 2*tradeoff - 4*promotional
```

独立した減点項（例: `- 8 * preDecisionOrPhotoShoot`）にしない理由:

- **二重計上を避けられる。** §2 の定義引き締めにより、フォト婚記事は `ceremonyDecision = false` にもなり得る。独立減点だとゲート 0 の上にさらに減点が乗り、`0 + 3 + 2 + 2 - 8 = -1` のように「宣伝記事より下」まで落ちる。フォト婚記事は的外れではあっても宣伝ではない
- **意味が一文で説明できる。** 「挙式・披露宴の中身の話であり、かつ既に式が決まっている前提の話であること」がゲートの条件になる。読者の状況そのものである
- **減点幅のチューニングが不要。** ゲート修飾子なら「ゲートを通さない」だけで、追加の重み定数が増えない

この変更で、フォト婚・前撮り・式場探しの記事は**ゲート不通過帯（0〜7点）に落ちる**。除外はされず、その帯の中では記事としての質（実体験・具体性・判断理由）の順に並ぶ。オーナー方針「低スコアは除外せず下に置くだけ」と整合する。

### 3.4 予想される順位変動

現在の上位5件に適用した場合の見込み:

| タイトル                   | 現在 | 変更後（見込み） | 理由                                   |
| -------------------------- | ---- | ---------------- | -------------------------------------- |
| フォト婚                   | 17   | 7                | ゲート不通過（撮影そのものの話題）     |
| 式場決定前の見積もり交渉術 | 17   | 7                | ゲート不通過（式場を決めるまでの段階） |
| 前撮り用小道具の毛筆文字   | 15   | 5                | ゲート不通過                           |
| Canva を活用した結婚式DIY  | 15   | 15               | 変わらず（当日のペーパーアイテム）     |
| BGMの重要性                | 15   | 15               | 変わらず                               |

結果として **BGM・DIY・スピーチ・演出・装花** が上位に来る。これが要望どおりの姿である。

ただしこれは**予測であって保証ではない**。実際の判定は LLM が行うため、バックフィル後に §6 の目視確認が必須である。

## 4. 保存先の問題（この計画で最も判断が要る箇所）

新しいブール値を `post_usefulness` テーブルに保存する必要があるが、**カラム追加ができない**。`scripts/apply-migrations-remote.mjs` は本番 Turso が news-watch と DB を共有しているため、安全装置として `CREATE TABLE` / `CREATE INDEX` 以外を実行しない（`ALTER TABLE` を含む文が現れた時点で exit 1）。

### 選択肢

| 案  | 内容                                                                   | 利点                                                                                                        | 欠点                                                                                                             |
| --- | ---------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------- |
| A   | 安全装置を緩め `ALTER TABLE post_usefulness ADD COLUMN` を許可         | スキーマが素直。1行で済む                                                                                   | 「このスクリプトは他人のテーブルを壊せない」という**構文レベルの保証が条件付きになる**。一度緩めると次回も緩める |
| B   | `post_usefulness_v2` を CREATE して切り替え                            | 安全装置に触れない                                                                                          | **判定項目を変えるたびに新テーブル**が増える。今回が初回の変更で、既に1日で発生している                          |
| C   | 判定項目を JSON 1カラム（`criteria_json`）に持つテーブルへ一度だけ移行 | **以後の判定項目の増減が DDL 不要**（純粋なコード変更になる）。既存の「重みはコード側に置く」設計思想と一貫 | 移行が1回必要。並び順の SQL が `json_extract()` になる                                                           |

### 推奨: C

判定項目が変わるのは例外ではなく通常運転である、という事実が既に出ている（有用度スコアを入れた翌日に本変更の要望が来ている）。B は変更のたびにテーブルが増える設計で、明確に誤り。A と C の比較では、

- A は「一度だけ緩める」つもりでも、判定項目が変わるたびに ALTER が必要なので**緩和が常態化する**
- C は移行コスト 1 回で、以後 DDL がゼロになる

`post_usefulness` は `posts` から完全に再生成できる派生データであり、バックフィルで作り直せる。移行のリスクは実質ない。

**C の実施内容:**

```sql
CREATE TABLE `post_usefulness_criteria` (
  `post_id`       integer PRIMARY KEY NOT NULL,
  `criteria_json` text NOT NULL,   -- {"firsthand":true,"ceremonyDecision":true,...}
  `signature`     text NOT NULL,
  `model_id`      text NOT NULL,
  `scored_at`     text NOT NULL
);
```

- 並び順の SQL は `json_extract(criteria_json, '$.ceremonyDecision')` 等で組み立てる（libSQL は JSON1 を持つ）
- 旧 `post_usefulness` は参照をやめた時点で**孤児テーブルになる**。共有 DB なので勝手に DROP せず、オーナーが手動で削除するか放置するかを判断する（43行なので放置コストは無視できる）
- 現行の重み定数（`USEFULNESS_*`）と `computeUsefulnessScore()` はそのまま使える。変わるのは読み書きの層だけ

**C を採らずスコープを小さく保つなら A。** その場合は許可する正規表現を `^ALTER\s+TABLE\s+post_usefulness\s+ADD\s+COLUMN\b` まで絞り、テーブル名をリテラルで固定すること。`posts` や `config` すら許可しない。

## 7. 意図的に採用しないもの

- **`postDecision` という正の極性での命名**: §3.1 のとおり、不明時に良記事が沈む
- **独立した減点項としての実装**: §3.3 のとおり、二重計上でフォト婚が宣伝記事より下に落ちる
- **フォト婚・前撮り記事のフィードからの除外**: オーナー方針は「下に置くだけ」。除外すると件数が痩せる
- **「式決定後か」を判定する専用の LLM 呼び出し**: 既存キュレーションと同一コールに乗せる。追加課金ゼロ
- **判定項目ごとの確信度スコア**: この規模では過剰
- **前撮り専用レーンの新設**: 需要が確認されていない。順序で十分
