## 1. 出発点 ── 「LLM の判断を公開してはいけない論理は無い」

**この指摘は正しい。** そして本計画は、これまでの議論が混同していた2つの問いを分離することから始める。

| 問い                                 | 答え                                                               |
| ------------------------------------ | ------------------------------------------------------------------ |
| **LLM の有用性判断を公開してよいか** | **よい。禁止する論理は無い**                                       |
| LLM の判断が正しいか                 | 測っていない。これは**品質**の問題であって、公開可否の問題ではない |

出力は既に plan 06 で「記事の内容」から「記事についての判断」に転換済みである。
判断とは**意見**であり、意見の公開に事前検証を要求する一般的な規範は存在しない。
書評・レビュー・レーティング・検索ランキング・レコメンドは、いずれも第三者検証なしに公開されている。
**アルゴリズムによる評価を無人で大規模に公開することは、むしろ web の標準的な振る舞いである。**

さらに本プロジェクトの設計は、意見として出す形式のうち**最も安全な側**にある。

- **公開するのは肯定的な選別のみ。** 不採用記事は「低評価」として表示されるのではなく、**単に存在しない**。
  不存在は主張ではないため、信用毀損の軸がほぼ閉じている（spec.md §9.8 のスコア非公開方針が結果的にこれを担保している）
- 元記事への導線が最優先 CTA であり、読者は一次情報に直接到達できる
- 非営利・広告なし

**したがって「人手レビューが無ければ公開できない」という前提は、本計画で明示的に撤回する。**

---

## 2. ただし「LLM の判断ではないもの」が3つ混ざっている ── ここが核心

§1 の論理が守るのは**「システム自身の判断」として出力されるもの**だけである。
現在のカードには、判断ではないものが3つ含まれている。**この3つだけは意見の自由では守られない。**

### 2.1 逐語タイトル ── 第三者が書いた文字列の無検閲公開

plan 06 §2.3 で `aiTitle` を廃止し、`originalTitle` の**逐語表示**に変えた。著作権上はこれが正しい。

しかし逐語表示とは、**元サイトが書いた任意の文字列が、無検閲で自サイトのカード上に載る**ということである。
これは LLM の判断ではない。`【PR】`、煽り、個人名、不適切表現がそのまま出る。

### 2.2 プロンプトインジェクション ── 攻撃者が書いた文字列

discovery 経路は**任意のページ本文を LLM に入力する**。その出力が無検閲で公開される経路が完成している。

インジェクションが成功した場合、出力は**もはやシステムの判断ではない**。攻撃者が書いた文字列を、
システムの判断であるかのように自ドメインで公開することになる。**§1 の「意見だから公開してよい」という論理が、ここでだけ成立しない。**

SEO・アフィリエイト事業者には明確な動機がある。**人手レビューはこの経路の唯一の防壁だった。**

### 2.3 クレジット ── 第三者への帰属は意見ではなく事実主張

「この記事は X が書いた」は意見ではなく**事実の主張**であり、誤れば第三者に実害が及ぶ。
plan 06 §10-2 / 著作権法48条の出所明示に直結する。

> **§2 の3項目は「意見の公開」ではないため、無人運転でも機械的な統制が要る。**
> 逆に言えば、**これ以外はすべて品質の問題であり、オーナーの裁量で決めてよい。**

## 3. 人手レビューが担っていたものの再分類

| 従来「人手が見る」としていた項目       | 実際の性質                                 | 無人運転での扱い                                                  |
| -------------------------------------- | ------------------------------------------ | ----------------------------------------------------------------- |
| 判定根拠の内容不一致・ハルシネーション | **品質**（読者への不親切・自サイトの信用） | 裁量。§6                                                          |
| 本文抽出の破損（ナビを本文と誤認）     | **品質**                                   | 裁量（ただし安いので推奨）。§6-Q1/Q2                              |
| §1.5 除外トピックの漏れ                | **品質**                                   | 裁量。既に `promotional` / `preDecisionOrPhotoShoot` で機械化済み |
| アフィリエイト専用サイトの混入         | **品質**                                   | 裁量。§6-Q3                                                       |
| **誤ったクレジット**                   | **第三者への実害**                         | **必須**。§5-M2                                                   |
| **規約・robots の変化**                | **アクセス側の義務**                       | **必須**。§5-M3                                                   |
| **インジェクション・無検閲文字列**     | **意見ではない出力**                       | **必須**。§5-M1                                                   |
| 削除要請・問い合わせへの応答           | **義務**（機械化不能）                     | **必須**。§5-M5                                                   |

**必須は4つだけである。** 残りはすべて「どこまで良い製品にしたいか」の話であり、法務でも安全性でもない。

## 4. 最も費用対効果が高いのは検証ではなく「開示」

**判断が自動であることを明示するだけで、誤りの性質が変わる。**

| 開示なし                                                             | 開示あり                                                                             |
| -------------------------------------------------------------------- | ------------------------------------------------------------------------------------ |
| 「この記事には実費の内訳がある」＝**事実の断定**。外れれば虚偽の主張 | 「本サイトの自動判定では実費の内訳あり」＝**開示済みの自動評価**。外れても評価の誤り |

検証装置を何段積むより、**カードまたはフィードに「判定は自動です」と1行置くほうが効く。**
コストはほぼゼロで、§1 の「これは意見である」という立場を、読者に対しても明示的なものにする。

**これを §5 の必須項目に含める**（M6）。実装は文言の追加のみ。

## 5. 必須の統制（第三者に害が及ぶ／意見ではない部分）

### M1. 無検閲の公開チャネルを閉じる

**逐語タイトルと `topicAnchor` は、外部が書いた文字列がそのまま出る経路である。**

- **タイトル公開フィルタ**: `【PR】` `[広告]` `#PR` 等の広告表記、NG 語パターンに合致するものは**公開しない**（取り込み自体は可、`status` を published にしない）
- **`topicAnchor` の語彙的接地**: アンカーの特徴語が**取得本文中に逐語で実在する**ことを要求し、無ければ棄却。
  日本語のため形態素解析に依存させず、**2文字以上の特徴語が本文に逐語包含されること**を条件にする
  - これはインジェクション対策としても働く（攻撃者は狙った文字列をページに置けるため万能ではないが、
    「本文に無い文字列は出せない」という上限を課せる）
  - **誤棄却率も同時に計測すること。** 厳しすぎる接地はスループットを静かに殺し、それ自体が障害になる
- **出力空間の閉包**: `rationaleText` は §6-Q5 のテンプレート化を採ればこの経路自体が消える

### M2. クレジットは構造化メタデータのみ

- `author` は JSON-LD / `meta` / `dc:creator` **からのみ**取得する。**LLM に推定させない**
- 解決できなければ `null` で非表示。**捏造しない**（plan 04 P2 で `sourceName` について既に実装済みの方針を `author` にも徹底する）
- 現状の実装がこれを満たしているか**確認すること**

### M3. アクセス規律と K2

- 実装済み: robots.txt 遵守（24h）、最小間隔、日次キャップ、条件付き GET、512KB 上限、連絡先入り UA、UA 偽装禁止、K1/K3/K4/K5/K6/K7
- **K2（規約変更検知）を実装する。** ただし生ハッシュ差分は**ノイズだらけで、無人運転下では誰も読まないアラートを量産する**。
  規約テキストを正規化してハッシュし、変化時のみ「自動アクセス・クロール・コンテンツ再利用を制限する変更か」だけを問う**限定分類**にかける
  - それでも低ノイズにできない場合、実効シグナルは robots + 403/429（実装済み）と割り切り、
    **K2 は「監視していた」という法的姿勢の記録**として位置づける。それ自体に価値がある
  - `source_policy.tos_hash` が**休眠カラムのまま残る状態は避ける**（実装済みに見えて動いていない、が最悪）

### M4. 客観的トリガによる自動撤回

**非公開化は可逆で、原文を出していない以上、下げて害を受ける者はいない。誤って下げるコストはほぼ0、誤って残すコストは信用と法務。非対称なので低い閾値で自動化してよい。**

即時自動非公開の対象（**すべて客観的事実であり、モデルの意見ではない**）:

- 元記事が 404 / 410
- robots.txt で当該パスが不許可に変わった
- 当該ホストで K3（401/451）が発火
- 元記事の本文ハッシュが大幅に変化（判定が陳腐化）
- 削除要請の受領

**再公開は自動化しない。撤回は自動、復帰は人間。** 撤回済み項目は sticky にする（さもないと発振する）。

### M5. 連絡先と撤回手段

**機械化できない義務**。無人運転でも消えない。

- 連絡先を公開する（UA に含める URL と一致させる）
- 受信箱を実際に読む
- **1コマンドで特定 URL / ホストを撤回できるツール**を用意する（緊急時に手作業で DB を触らない）

## 6. 品質の統制（オーナーの裁量・安い順）

**ここから先は「必須」ではない。** 実施しなくても第三者に害は及ばない。**製品の質と自サイトの信用の問題である。**

| #      | 施策                                                                                                                                                                                                                                                                                                                                                                                        | コスト                       | 効果         | 推奨         |
| ------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------- | ------------ | ------------ |
| **Q1** | **抽出品質の決定的ゲート** ── リンク密度・定型行反復率・最小本文長・抽出文字数/生HTML比などで判定し、**`evidenceSufficient` を LLM の自己申告ではなくここから決定的に計算する**（LLM は「自分が何を持っていないか」の判定が苦手）                                                                                                                                                           | 低                           | 高           | **強く推奨** |
| **Q2** | **K8（yield 崩壊検知）** ── ホスト単位の採用率・`promotional` 率・`author` 取得率が**そのホスト自身のベースラインから乖離**したら自動停止。最小分母（判定30件以上等）を課さないと小標本ノイズで健全ホストを殺す。データは `discovery_run` に既にある                                                                                                                                        | 低                           | 高           | **強く推奨** |
| **Q3** | **ホスト allowlist** ── discovery は新規ホストを自動追加しない。追加は明示的なコミット＝「よっぽどのこと」であり日常の目視とは別物。**アフィリエイトサイト混入が構造的に消える**                                                                                                                                                                                                            | 低                           | 高           | **強く推奨** |
| **Q4** | **日次公開上限＋ホスト別シェア上限** ── 最も安価な被害半径の限定。1ホスト423件×通過率50%でフィードが特定媒体に埋まると、個々のカードが正しくても「中立キュレーション」という主張が偽になる（per-item チェックでは見えない）                                                                                                                                                                 | 低                           | 中〜高       | **強く推奨** |
| **Q5** | **`rationaleText` のテンプレート化** ── 仕様上すでに数値禁止・60〜90字であり、情報量はほぼ 6 boolean の関数。人が書いたフレーズバンクから boolean ベクトルで決定的に選べば、**ハルシネーション面が消滅**し §10-3 が証明可能になる。さらに踏み込めば、チップが boolean を表示している以上 per-card の根拠文は冗長で、**判定基準の説明をページに1回置いてフィールドごと廃止**という選択もある | 中                           | 高           | 検討         |
| **Q6** | **モデルのピン留め** ── モデル/プロンプト変更をコード変更として扱う。これが無いと Q7 以降の監視が意味を失う                                                                                                                                                                                                                                                                                 | 低                           | 中           | 推奨         |
| **Q7** | **golden set と較正**（§8）                                                                                                                                                                                                                                                                                                                                                                 | **人手40〜60件（一度きり）** | 誤り率の実測 | §8 で判断    |
| **Q8** | **交差モデルによるシャドウ再判定** ── ドリフト検知。ただし測れるのは一致率であって正解率ではない（誤りが相関する）。**ベースラインからの変化のみを見る**                                                                                                                                                                                                                                    | 中                           | 中           | Q7 の後      |

## 7. `pending` の廃止

**誰も処理しない `pending` は状態ではなくゴミである。** 現在「判定不能なら pending 保存」としているが、無人運転では永久に溜まる。

**`pending` を廃止し、「TTL 付き再試行キュー」＋「理由コード付き終端棄却」に置き換える。**

| 原因                                  | 扱い                                                                                                                             |
| ------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------- |
| 一時的技術障害（timeout / 5xx / 429） | 指数バックオフで最大3回・72時間、以後 `dropped(transient)` で終端                                                                |
| 抽出不足 / `evidenceSufficient=false` | ページが変わらない限り再試行しても変わらない。**再試行禁止**、即終端                                                             |
| 接地失敗・判定不一致                  | **終端棄却。ここでの再試行は自分の安全チェックに対するリサンプリングになる**（実装時に最も誘惑される誤り。明示的に禁止する）     |
| 真に曖昧                              | 解決者が居ない以上**棄却**。非営利フィードで偽陰性のコストは実質ゼロ、偽陽性のコストは信用。**非対称なので積極的に棄却してよい** |

**理由コードはそのまま Q2 のテレメトリになる**（`dropped(extraction_low_quality)` の急増＝そのホストの DOM 変更）。
レコード（URL＋理由）は恒久保持（再取得ループ防止）、**本文は従来どおり非保存**を維持する。

## 8. 較正について ── 正直に書く

### 8.1 較正しない場合に失うもの

**誤り率が未知のまま運用することになる。** 現在の実測は「ゲートを通るか」だけで、
**「LLM がその記事について正しく述べているか」は一度も測っていない**。n=8 の 4/8 は 95%CI がおよそ 16〜84% で、情報はほぼゼロである。

### 8.2 それでも公開してよい

**§1 のとおり、これは意見であり、意見の公開に事前検証は要らない。**
較正しない選択は「品質を測らずに出す」であって「してはいけないことをする」ではない。

**ただし、公開する主張の強さを、測っていない事実に合わせること。** §4 の開示がこれを担保する。

### 8.3 やるなら一度きりで済む

「日常的に目視しない」と「一度も接地点を作らない」は別の活動である。やるなら以下の形が費用対効果が高い。

- **層化サンプル 40〜60件**（無作為一様は明白な陰性に予算を浪費する。ゲート通過側に重みを置く。例: 通過40件＋境界付近の不通過15件）
- **フィールド別にラベル**（6 boolean 各々の正誤＋アンカーの忠実性）。必要なのは総合点ではなく、**ゲート2項（`ceremonyDecision` / `preDecisionOrPhotoShoot`）の精度**
- **凍結して golden set 化**。うち15件前後は**チューニングに使わない hold-out** として残す（さもないと golden set は訓練セットに劣化する）
- 更新はモデル/プロンプト変更時に10〜15件追加のみ

精度の目安: **粗い破綻（精度70%未満）の検出なら30件で十分な検出力がある。「精度90%」を主張するには100件超が要る。**
40〜60件は「重大な破綻は否定できるが、品質は保証できない」帯である。

### 8.4 較正が本当に不要になる唯一の設計

**機械が記事について何も主張しないこと。** 構造的フィルタのみの純粋なリンクフィード（タイトル＋媒体＋リンク）なら較正は不要になる。

**判定チップを出すという選択は、較正と監視の恒常コストを引き受けるという選択と不可分である。** ここは曖昧にしない。

## 9. 段階設計

### Stage 0 — 必須統制（§5）

M1〜M6。**各ゲートは意図的に壊して落ちることを確認するまで完了と見なさない**（AGENTS.md）。

### Stage 1 — 安価な品質統制（§6 Q1〜Q4、Q6）

いずれも人手不要・データ不要。**Stage 0 と同時に進めてよい。**

### Stage 2 — 監督付き自動（4週間 または 公開200件）

全自動で公開するが**日次上限を低く**（≤10件）。オーナーは item ごとではなく**フィード全体を時々眺めるだけ**。
確認するのは (a) 客観トリガによる自動撤回がゼロか (b) ホスト分布が上限内か (c) `dropped` 理由コードの分布が安定しているか。

### Stage 3 — 無人運転

Stage 0・1 が実装済みかつ**意図的破壊で検証済み**、Stage 2 がクリーンであること。

### 無人運転後も残る人的義務（消せない3つ・合計で月1時間未満）

1. **受信箱を読む**（削除要請・問い合わせ）
2. **アラートに応答する**（ホスト自動停止・撤回の通知）
3. **モデル/プロンプト変更時に回帰を回す**（Q7 を採用した場合）

**これは「よっぽどのことがない限り目視しない」と完全に両立する。**

## 10. 意図的に採用しないもの

- **「人手レビューが無ければ公開できない」という前提** ── §1。撤回する
- **不採用記事の否定的評価の公開** ── 不存在は主張ではない。この設計を維持する（信用毀損の軸を閉じ続ける）
- **モデルの意見をトリガとする個別記事の自動撤回** ── §5-M4。未検証の意見を別の未検証の意見で上書きするだけ。
  **個別＝客観的証拠、集団＝統計的証拠**、という切り分けを規則にする
- **撤回の自動復帰** ── §5-M4。撤回は自動、復帰は人間
- **接地失敗・判定不一致に対する再試行** ── §7。自分の安全チェックへのリサンプリングになる
- **`pending` を「後で人が見る」置き場として残すこと** ── §7
- **全件の交差モデル監査** ── コストに見合わない。無作為5〜10%で足りる（Q8）
- **`source_policy.tos_hash` を休眠カラムのまま放置すること** ── §5-M3

## 14. 「緑だが機能していなかった」テストの事例（再発防止の記録）

本作業で意図的破壊検証を行った際、CI 上は緑のまま実際には機能していなかった箇所が2件見つかった。
**いずれも意図的破壊検証によってのみ発見できた。** 通常のテスト実行だけでは検知できない種類の欠陥として記録する。

1. **K2（規約変更検知）**: テストが `seedPolicyForTos()`（テスト専用ヘルパー）で `source_policy.tosUrl` を手動注入していたため、K2 の判定ロジック自体は緑だった。しかし本番の摂取経路では `tosUrl` は allowlist から解決されるまで常に null であり、**本番経路では一度も発火しない状態だった**。allowlist 側を真実の源として DB の値を上書き解決するよう修正し（spec.md §11-1）、テストも実際の摂取経路を通す形に修正した。
2. **日次公開上限**: テストが `DAILY_PUBLISH_CAP` / `HOST_DAILY_SHARE_MAX` という定数そのものから期待値を導出していたため、**上限を実質無効な値（999999 等）に戻してもテストは落ちなかった**（テストが「定数と実装が一致していること」しか検証しておらず、「上限が現実に機能すること」を検証していなかった）。境界値を固定リテラルで検証するテストに修正した。

いずれも AGENTS.md の「ゲートが緑であることと、ゲートが機能していることは別である」という原則の具体例であり、新しい検証機構を追加する際は同種の欠陥（テストヘルパーが本番経路を迂回する／期待値が実装の定数から自己導出される）がないか確認すること。
