# 10. 公開ポリシーの再診断 ── 「厳密すぎる」ではなく「粗い」と「観測不能」

- 対象: `wedding-trend`（本プロジェクト）
- 参照: `shared_plan/07-unattended-operation.md`（§5〜§8）、`shared_plan/09-extraction-calibration-and-observability.md`（§2-2・§5）
- 作成日: 2026-08-26
- 前提コミット: `f40b89c`
- 状態: **一部実施。** 2026-08-29、オーナー判断でゲート大幅緩和と日次公開制限のサーキットブレーカー化を実施した（spec §11 項1・項4）:
  - 抽出品質ゲート: `MIN_EVIDENCE_INPUT_CHARS` 80→30、`MAX_LINK_DENSITY` 0.25→0.70、`MIN_PARAGRAPH_COUNT` 3→1
  - トピックアンカー: clickbait denylist 撤廃、長さ下限 12→6、タイトル冗長性チェックを非ブロッキング化（接地検証は維持）
  - タイトル公開フィルタ: 広告・PR キーワード拒否を撤廃（制御文字・記号連打・過剰絵文字・空のみ棄却）
  - `HOST_DAILY_SHARE_MAX` 廃止、`DAILY_PUBLISH_CAP` 15→150（供給スロットルから暴走検知サーキットブレーカーへ）、目標供給量「15件/日」撤廃
  - 「集約レベルの中立性」を運用ポリシーから撤回（README / AGENTS.md も追随）

## 1. 問題の再定義 ── 「厳密すぎる」は誤診である

「公開ポリシーが厳密すぎるのではないか」という問いから出発すると、閾値をいくつ緩めても
「まだ厳密すぎるのでは」という問いが再生産される。**基準がないからである。**

実測（§3）が示しているのは厳密さではない。

1. **終端棄却 76 件のうち 73 件（96%）が `extraction_insufficient`。** これは「記事の質が低い」という
   編集判断の結果ではない。**HTML から本文を取り出せなかった**という抽出器の失敗である。
   フィルタリングの帰結が、意味論ではなく相手サイトの DOM 構造の偶然によって決まっている
2. しかも `extraction_insufficient` は `too_short` / `link_density` / `paragraph_count` / `container_not_found` の
   どのサブ条件で落ちたかが**記録されていない**。どの条件が効いているかを測れていないものを、
   校正しようとしている状態にある
3. **目標フィード供給量（件/日）が定義されていない。** 目標がなければ「厳密すぎる」は真偽の判定さえできない
   命題である。閾値の数値の話から始めてはならない

**したがって本計画の軸は「閾値を緩める」ではない。「観測を作り、目標を決め、その上で判断する」である。**
言い換えれば診断は「厳密すぎる」→「**粗く、かつ観測できていない**」である。

## 2. 目標の定義 ── 現時点では未定であり、これを決めることが最初の作業である

歩留まり・閾値・棄却理由のどれを議論するにも、比較対象となる基準線が要る。基準線は
**目標フィード供給量（件/日）とホスト分散の許容範囲**である。

**現時点でこれは未定である。** §6 の測定計画・§9 の変更手順は、この目標値が定まっていることを
前提に組んである。**本計画の実行順序上、目標の確定（M1 相当ではなく計画外の意思決定事項）が
すべてに先行する。** 目標が決まらない限り、§7 の校正表のどの項目も「変更判断基準」を評価できない。

## 4. 「67% が埋没」の読み方 ── 矛盾ではなく設計の帰結

これは矛盾ではない。**二値ゲートがランキングに偽装されている**状態である。

`src/lib/constants.ts` の `USEFULNESS_GATE_BONUS = 12` は強支配不変条件として設計されている
（plan 09・spec.md 参照。減点合計の最大値 `preDecisionOrPhotoShoot`(3) + `promotional=heavy`(4) = 7 に対し、
12 − 4 = 8 > 3 + 2 + 2 = 7 が成立し、ゲート通過は必ずゲート不通過に勝つ）。
その結果、ゲート通過 29 件は不通過 58 件に**必ず**勝つ。これは順位付けではなく、事実上の可視面の切断である。

問題は2つに分解できる。

1. 実質的な編集判断が LLM の `ceremonyDecision` ブール出力1個に全依存しており、
   そのキャリブレーション（人手ラベルとの一致率）が**一度も測られていない**。33% という通過率が
   高すぎるのか低すぎるのか、誰も根拠を持って答えられない
2. **「棄却 0 件」は寛容さの証拠ではない。** 編集方針が公開/非公開の境界に一切効いていない証拠である。
   編集方針は表示順位という観測しづらい場所に押し込まれ、通過率が妥当かどうかを検証する
   フィードバックループが存在しない

さらに出口が詰まっている。`DAILY_PUBLISH_CAP = 10` と `HOST_DAILY_SHARE_MAX = 0.5` により、
mwed.jp から取れるのは最大5件/日である。pending 242 が発散している状況で入口の閾値を緩めても、
増分は CAP に当たって消えるだけであり、供給量は改善しない（§8）。

## 5. ゲートの分類

### 5-1. 法務要件（a）── 検討対象外

以下は spec.md §10 に定義された仕様要件であり、実装判断で緩めてはならない。
**歩留まり改善の文脈に法務ゲートを一度でも並べると、次の担当者が「トレードオフ対象」と誤読する。**
本節で明示的に切り離す。

- タイトルフィルタ（無検閲公開の防止。plan 07 §5-M1）
- `topicAnchor` の語彙的接地（プロンプトインジェクション対策・個人情報対策。plan 07 §5-M1）
- `author` は構造化メタデータのみ（LLM に推定させない。plan 07 §5-M2）
- 根拠文（`rationaleText`）の数値禁止
- 本文コンテナ抽出（`extractArticleContainer()`。plan 09 §1）

これらに加えて、強支配不変条件（`USEFULNESS_GATE_BONUS` の不等式）も**不変条件**として本節に置く。
値を動かすこと自体は法務要件ではないが、崩す変更は §7 の校正対象に含めず、§4 の設計判断として
別途扱う（§13-5 参照）。

### 5-2. 編集方針（b）── 見直し対象。ただし最後

- ホスト allowlist（`src/lib/constants.ts` の `HOST_ALLOWLIST`）
- 記事パス allowlist
- `MIN_EVIDENCE_INPUT_CHARS = 80`
- `MAX_LINK_DENSITY = 0.25`
- `MIN_PARAGRAPH_COUNT = 3`
- 有用度ゲート（`ceremonyDecision`）
- `preDecisionOrPhotoShoot` 減点3
- `promotional = heavy` 減点4
- 加点（`firsthand` 3 / `specific` 2 / `tradeoff` 2）
- `HOST_DAILY_SHARE_MAX = 0.5`

**「最後」とする理由**: §1 の診断が正しければ、96% の棄却は抽出器に起因しており、
(b) の閾値をどう動かしても分母（`extraction_insufficient` を除いた記事群）はほぼ変わらない。
計装（§6）と出口の整合（§8）が先に効くはずの領域を触る前に (b) を変更すると、
効果の帰属が不能になる（§13-6 と同型の誤り）。

### 5-3. 運用安全弁（c）── 最初に着手。ただし緩める方向ではなく計装として

- kill gate K1〜K6（`src/lib/sources/access-discipline.ts`）
- `DAILY_REQUEST_CAP_PER_HOST = 50`
- `DAILY_PUBLISH_CAP = 10`
- 本文サイズ上限 512KB

(c) は歩留まりを直接左右する対象ではなく、供給量の天井を決める装置である。§8 で出口の整合として
扱うが、閾値そのものを緩める対象ではない。

## 6. 計装 I1〜I4

### I1. 棄却サブ理由の分解記録

`extraction_insufficient` を `too_short` / `link_density` / `paragraph_count` / `container_not_found` の
どれで落ちたかまで分解して記録する。現状はこの内訳が記録されておらず、96% という数字の中身が
不明である。実装対象は棄却経路（`src/lib/pipeline/discovery-ingest.ts` 系）の理由コード付与箇所。

### I2. shadow 記録（観測モード）

閾値を適用せず、値だけを全件記録する観測モード。plan 09 §2-1 で `link_density` 等の通過時記録は
計画済みだが、**棄却されうる値も含めて全件記録する**点を明確にする（通過方向でしか観測しないと
plan 09 §5 の「常に赤いゲートも未検証」と同型の盲点が再発する）。

### I3. 反実仮想再生ハーネス

既存 `posts` 全件に新しい閾値セットを再適用し、`published` / `rejected` の差分を機械的に算出する
仕組み。§9-S4 の実行基盤。CI から実行できる形にする（§9 参照）。

### I4. yield 崩壊検知

plan 07 §6-Q2（K8: ホスト単位の採用率・`promotional` 率・`author` 取得率のベースライン乖離検知）は
**未実装**（plan 07 §11 完了判定に記載なし）。生データは `discovery_run` テーブルに既に蓄積されている。
本計画の §9-S7（ロールバック条件の事前定義）は I4 の存在を前提にするため、**I4 は本計画の他の変更に
先行して実装する。**

## 9. 変更手順 S0〜S7

閾値を1つでも変更する場合、以下を固定手順とする。省略しない。

```
S0 目的の宣言   何のために変えるか（目標供給量に対する不足量）を数値で書く
S1 計装        値を全件記録。閾値は適用しない（観測専用デプロイ）
S2 分布取得    ホスト別 n≥30。min/p5/p50/p95/max を spec.md に転記
S3 判断        観測極値の直下に置かない。マージン根拠を1文で書く
S4 反実仮想再生 既存 posts 全件に新閾値を再適用し、published/rejected の
               差分を出す。本番投入前に「何件が何に変わるか」を確定させる
S5 変更        spec.md に 値・n・分布・マージン・守っている失敗モード を同時記載
S6 意図的破壊   閾値の両側の境界値テスト。緩めた側で実際に落ちることを確認
S7 事後監視    ロールバック条件を数値で事前定義。yield 崩壊検知で自動発火
```

特に強調する3点:

- **根拠なき閾値の禁止**: spec.md に n と分布とマージン根拠が書けない数値は、変更どころか存在を
  許さない。書けないなら廃止候補である（§8 の C5〜C8 が該当）
- **S4 の反実仮想再生を CI に載せる**: §13-2 に記録した過去2件の事故は、既存データへの再適用を
  1回やれば投入前に見えていた。最も費用対効果の高い再発防止策である
- **S7 のロールバック条件の事前定義**: yield 崩壊検知（I4）は本計画の前提条件として、他の閾値変更に
  先立って実装する（§6-I4 参照）

## 11. 完了判定

**「閾値を緩めた」を完了条件にしない。** 棄却を減らせば歩留まりは定義上必ず上がるため、
歩留まり上昇はトートロジーであり完了の証明にならない。完了は「**閾値が根拠を持つ状態になったこと**」
で定義する。

- [ ] 目標フィード供給量が数値で定義され spec.md に記載されている
- [ ] 全棄却が単一のサブ理由まで分解して記録されている
- [ ] (b) の全閾値について、n・分布・マージン・守っている失敗モードが spec.md に記載されている。
      記載できなかったものは廃止されている
- [ ] mwed.jp の 16.7% が「抽出器の不具合」か「記事の性質」かが判定済みで、根拠が記録されている
- [ ] 反実仮想再生ハーネスが存在し、CI から実行できる
- [ ] yield 崩壊検知が実装され、意図的破壊テストで発火が確認されている
- [ ] `ceremonyDecision` の人手ラベル一致率が測定され、33% 通過率の妥当性に結論が出ている
- [ ] 変更した各閾値にロールバック条件が数値で定義されている
- [ ] pending 発散が解消されている、または「意図的に捨てる」方針として明文化されている
- [ ] `rate_capped` が retry_queue から分離され、retry メトリクスが意味を回復している
- [ ] 「公開ポリシーは厳密すぎたか」への回答が、目標供給量との対比で数値付きで spec.md に残っている

最後の項目について、**Yes でも No でも完了である。** 「No だった（本当の問題は抽出器だった）」で
終わるのが正常な結末である可能性が高い、と明記しておく。§1〜§4 の実測が示す構図（棄却の96%が
抽出失敗、有用度ゲートは0件棄却）は、この結末を強く示唆している。

## 13. 意図的に採用しないもの / 失敗の記録

### 13-1. 意図的に採用しないもの

1. **目標供給量を定義せずに閾値を緩める** ── 基準がなければ緩めた後も「まだ厳密すぎるのでは」が
   無限に続く
2. **mwed.jp の n=5 の分布で共通閾値を決め直す** ── `MAX_LINK_DENSITY` と
   `RATIONALE_TEXT_MAX_CHARS=150`（plan 09 §5）の失敗の三度目になる
3. **法務ゲート (a) を歩留まり改善の検討対象に入れる** ── 議題に載せた時点で負け
4. **有用度ゲートを二値棄却に昇格させる** ── キャリブレーション未検証の LLM ブール出力を
   終端ゲートにするのは `boilerplateLineRatio` と同型（非決定的な値を破壊的閾値に使う）
5. **埋没解消のために `USEFULNESS_GATE_BONUS=12` を下げる** ── 強支配不変条件が壊れ、スコアの
   意味論が失われる。直すのは重みではなくゲート判定の精度かフィードの提示設計
6. **複数の閾値を同時に変更する** ── 効果の帰属が不可能になり、次の失敗記録が書けなくなる
7. **歩留まり（採用率）の上昇を成功指標にする** ── 定義上必ず達成されるので指標として無価値
8. **retry_queue の TTL 延長で `rate_capped` 問題を糊塗する** ── 原因は分類の誤りであり TTL は症状
9. **mwed 専用パーサの追加と一般閾値の緩和を同じ変更に混ぜる** ── どちらが効いたか永久に分からなくなる
10. **反実仮想再生なしの本番投入 / 本番でのみ検証する** ── 過去2件の事故は両方これ
