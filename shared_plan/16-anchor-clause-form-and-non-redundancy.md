## 1. 発端

オーナーの指摘は次の通り（原文）。

> shared_plan/15 では要約を変更したが、結果的にあまりに淡白。審査もハルシネーションを恐れる
> あまりまだ厳しすぎるので、そこも見直しつつ、表題とは被らない内容かつ魅力的な、
> クリックを促すような内容が入るように再検討を

要求は4点に分解できる。

- R1. **淡白さの解消**（15 の実装結果が無味乾燥である）
- R2. **審査（grounding gate）の見直し**（ハルシネーション恐怖による過剰な厳格さ）
- R3. **表題と被らないこと**（現在アンカーがタイトルの言い換えになっている）
- R4. **魅力的でクリックを促すこと**

本プランの結論を先に述べる。**R2 を単独で実施してはならない。** 調査の結果、
淡白さの主因は審査の厳しさではなく、**`shared_plan/15` が §10-3 に入れた
「体言止め」という要求そのもの**であると判明した（§3-4 H0、§3-5 で実測により裏付け）。

裸の名詞句は構造上「記事の話題を名指す」ことしかできず、話題はタイトルが既に名指している。
つまり「体言止めで話題を名指せ」は、**タイトルの言い換えを作れと命じているに等しい**。
実測でも、公開77件のうち **57% が裸の名詞句（平均重複率 0.886・平均8.6字）**である一方、
**節（述語を含む）は 9% しかなく、平均重複率 0.570・平均15.1字**と明確に良い。
**淡白さは事故ではなく制度化されていた。**

したがって順序は次の通りである。

1. **プロンプトを直す**（体言止めの撤回・few-shot の導入）— これが最大の ROI
2. **審査の「形」を変える**（閾値を下げるのではない。§4-4-D2）
3. **表題との非重複を機械的に強制する**（現在どこにも存在しない機構）

**R2 を先に、単独でやってはならない。** 現状の LLM は経路によっては
og:description 1文しか読んでいない（§2-3）。原文を見ていない LLM の審査だけを緩めれば、
アンカーが豊かになることはなく、緩和分はそのまま捏造（ハルシネーション）の余地になる。

### 2-5. grounding gate（`src/lib/publish/gate.ts:265-286`・逐語）

```ts
export function checkAnchorGrounding(topicAnchor: string, bodyText: string): GateResult {
  if (containsPersonalInfoPattern(topicAnchor)) {
    return { ok: false, reason: "anchor_ungrounded", missingTerms: [] };
  }
  const terms = extractFeatureTerms(topicAnchor);
  if (terms.length === 0) {
    return { ok: false, reason: "anchor_ungrounded", missingTerms: [] };
  }
  const normalizedBody = normalizeForGrounding(bodyText);
  const requiredTerms = terms.filter((term) => !CONNECTOR_ALLOWLIST.has(term));
  const missingTerms = requiredTerms.filter(
    (term) => !normalizedBody.includes(normalizeForGrounding(term)),
  );
  if (missingTerms.length > 0) {
    return { ok: false, reason: "anchor_ungrounded", missingTerms };
  }
  return { ok: true };
}
```

### 3-4. 因果の特定

本プランの中核となる認識。**H0 が主因であり、H1〜H4 はそれを増幅する条件である。**

- **H0. 「体言止め」という要求そのものが、表題との重複を仕様として要求していた。**
  §3-3 のうまくいっている例はすべて**節（述語を含む）**であり、§3-2 の失敗例はすべて
  **裸の名詞句**である。裸の名詞句は構造上「記事の話題を名指す」ことしかできない。
  そして話題はタイトルが既に名指している。したがって
  「体言止めで話題を名指せ」（`1337ef2` による §10-3 改定）は、
  **タイトルの言い換えを作れと命じているに等しい**。淡白さは事故ではなく制度化されていた。
  これは gate を1ミリも触らずにプロンプト側だけで解ける。

- **H1. 原文の痩せは増幅要因ではあるが、重複の主因ではない（§3-5 の層別で実証的に否定された）。**
  og:description 1文しか読んでいない LLM に「本文に実在する語句のみで構成せよ」と
  命じれば、実質的に使える語はタイトル由来の語しか残らない。アンカーがタイトルの
  部分文字列へ収束するのは規則の必然的帰結である。`anchor_ungrounded` が
  3.2% しかないのは gate が「落としている」のではなく「**萎縮させている**」ことの現れであり、
  低い棄却率はむしろ症状である。したがって審査だけを緩めても淡白さは直らず、
  原文を見ていない以上、緩和分はそのまま捏造の余地になる。

  ただし**萎縮の発生源は gate の実装ではなくプロンプトの文言である**。
  gate は `CONNECTOR_ALLOWLIST` で助詞・フレーミング名詞を免除しているが、
  **LLM はその存在を知らされていない**。プロンプトが告げているのは
  「本文抜粋に実在する語句のみで構成し、逐語一致を機械的に検証する（未一致語があると非公開）」
  という gate より厳しい脅し文だけである（§2-1）。
  **プロンプトの契約と gate の契約が乖離しており、乖離分がまるごと萎縮になっている。**
  したがって `CONNECTOR_ALLOWLIST` をいくら拡張しても gate は緩むが萎縮は 1ミリも緩まない。

- **H2. `9d7aac0` の backfill には劣化の経路があるが、規模は当初の見立てより小さい（§3-5 で訂正）。**
  backfill は `originalTitle + ""` を照合先とするため、`original_excerpt` が NULL の
  レコードでは**タイトルのみ**が照合先になる。`9d7aac0` の safe-filter は
  「grounding に落ちる新アンカーは書かない」だけであり、
  **タイトルの部分文字列は grounding を自明に通過する**ため、劣化した安全なアンカーは
  素通りする。**safe-filter は劣化を防いでいない**（この批判は維持する）。

  ただし当初「discovery 経路の投稿が広範に劣化した」と見立てたのは**誤りだった**。
  §3-5 の通り **discovery 経路は本番で1件も稼働していない**。
  該当するのは `original_excerpt` が NULL の公開18件に限られる。
  **機構としての危険は実在するが、現時点の被害はそこまで大きくない。**
  したがって D8/D9 は「起きた事故の修復」ではなく
  **「D7 でフェッチ範囲を広げた瞬間に全経路で顕在化する事故の予防」**として位置づける。

- **H3. 「表題と被らない」ことを担保する機構がどこにも存在しない。**
  grounding は「原文にある語か」しか見ず、「タイトルと同じ語か」は一切見ない。
  それどころか照合コーパスがタイトル中心である以上、gate はタイトル語の使用を
  **積極的に奨励する方向**に働いている。

- **H4. アンカー長の下限が無い**（`z.string().min(1)`）ため、`結婚` のような2字アンカーが通る。

### 3-5. 因果の実証（層別計測・2026-08-28）

§3-4 の H0〜H2 を検証するため、公開77件を**コーパスの厚さで層別**した。
重複率の算出式は §3-1 と同一（記号・空白除去後、
**アンカー側の文字2-gram のうちタイトルにも出現するものの割合**。Jaccard ではない）。

#### (1) 重複はコーパスの厚さで説明できない — **H0 を支持し、H1 を主因から降ろす**

| 層                            | n   | 重複率 mean | median    | ≥0.7              | アンカー字数 mean/median |
| ----------------------------- | --- | ----------- | --------- | ----------------- | ------------------------ |
| A: `original_excerpt` が NULL | 18  | **1.000**   | 1.000     | **18/18（100%）** | 12.3 / 10.5              |
| B: NOT NULL かつ 200字未満    | 47  | 0.802       | 1.000     | 34/47（72.3%）    | 11.1 / 10                |
| C: **200字以上**              | 12  | **0.837**   | **1.000** | **9/12（75.0%）** | 10.2 / 10                |

| 経路               | n   | 重複率 mean | median | ≥0.7           |
| ------------------ | --- | ----------- | ------ | -------------- |
| `blog/google-news` | 3   | 1.000       | 1.000  | 3/3（100%）    |
| `blog/note`        | 59  | 0.809       | 1.000  | 43/59（72.9%） |
| `blog/evergreen`   | 15  | 1.000       | 1.000  | 15/15（100%）  |

**結論: 層Aが最も高いが、層B・層Cも mean 0.80〜0.84・median 1.000・
≥0.7 が 72〜75% と、コーパスが厚い層でも重複は解消していない。**
原文が200字以上ある層Cですら 75% が高重複である。
**したがってコーパスを厚くするだけでは重複は直らず、
原因の中心はプロンプト規則（H0）にある。**

#### (2) 「節 vs 裸の名詞句」— **H0 の直接的な裏付け**

| 分類                 | n             | 平均重複率 | 平均文字数 |
| -------------------- | ------------- | ---------- | ---------- |
| **裸の名詞句**       | **44（57%）** | **0.886**  | **8.6字**  |
| その他               | 26（34%）     | 0.874      | 14.6字     |
| **節（述語を含む）** | **7（9%）**   | **0.570**  | **15.1字** |

**§3-3 の観察は実データで成立した。** 節は重複率が 0.32 ポイント低く、文字数は 1.8倍長い。
そして現状の **57% が裸の名詞句**である。H0（体言止め要求が重複を制度化した）が主因であることの直接証拠。

#### (3) カードは `topicAnchor` 無しで既に成立している — **D5 の前提が確認された**

`feed-card.tsx:51-65` の `{card.topicAnchor && (...)}` により、null のときは
アンカーと「AI判定」バッジのブロックが**丸ごと描画されない**。
親は `flex flex-col gap-3` のため gap も発生せず、固定高さの空白は残らない。

さらに **`post_rationales` 行を持たない公開投稿が既に7件実在し、
本番で無アンカー描画されている**（`blog/note` 4件・`blog/google-news` 1件ほか）。
spec にも topicAnchor を公開の必須要件とする記述は無い（L712/714/751 は描画規則のみ）。

> **D5（棄却せず null へ degrade）は、新しい状態を作るのではなく
> 既に存在する状態を正式化するだけである。**

#### (4) `discovery-ingest` は本番で1件も稼働していない — **H2 の規模を訂正**

`posts` の `source_type`/`source_id` は `blog/evergreen` / `blog/google-news` / `blog/note` の
3種のみで、`discovery-ingest.ts` が書き込むホスト別 `sourceId` は**存在しない**。
`reason` にコロン付き接尾辞（`extraction_insufficient:text_length` 等）を持つ行も**DB全体で0件**。

> **`MIN_EVIDENCE_INPUT_CHARS`（80）/ `MAX_LINK_DENSITY`（0.25）/ `MIN_PARAGRAPH_COUNT`（3）
> という3つの閾値は、本番データに一度も適用されていない。**

これは D7 の論拠に影響する。「discovery 経路は既に本文を取得しているから先例がある」は
**コード上の先例であって運用上の実績ではない**。§4-4-D7 はこの点を割り引いて読むこと。

#### (5) 棄却92件の正体 — **D7 の投資対効果が二重になる**

`extraction_insufficient` 92件（dropped の 96.8%）は、
`computeEvidenceSufficiency()` の3閾値によるものでは**なく**、
`ingest.ts:536-554` / `evergreen.ts:361-367` の**「抜粋が空文字列でないか」という二値判定のみ**に起因する。

| 経路               | 件数 |
| ------------------ | ---- |
| `blog/evergreen`   | 72   |
| `blog/google-news` | 20   |
| `blog/note`        | 0    |

> **記事本文を取得すれば、この92件は救済されうる。**
> オーナーの問いはアンカーの文言だったが、**データ上の最大の損失はこちらにある**。
> D7（原文の確保）は、アンカーの改善と棄却92件の救済を同時に回収する。

## 4. 設計判断（`@oracle` レビュー済み）

### 4-1. 統一原理

> **答えを伏せ、問いを開示する。**（結論ではなく、視点・場面・争点を書く）

R4（魅力）・§10-3（ゼロクリック化の回避）・中立キュレーションの3つは、
衝突するトレードオフではなく**同じ規則の3つの側面**である。
クリックを生むのは情報の提供ではなく**情報の非対称の可視化**であり、
読者が「自分がまだ知らない何かが、そこに具体的にある」と分かった瞬間に起きる。

- 結論・数値・評価は書かない → ゼロクリック化の回避＋中立
- 「誰の視点で」「どんな場面の」「何が争点か」は書く → 魅力
- 記事内に**実在する**視点の言語化に留め、媒体の評価を足さない → 中立

### 4-2. 煽りと魅力の境界（この一線で引く）

> **煽りは媒体が付け加えた価値評価。魅力は記事に実在する視点の忠実な言語化。**

|                                      | 例                                                                       |
| ------------------------------------ | ------------------------------------------------------------------------ |
| **禁止**（媒体による情動・価値付与） | `衝撃` `必見` `実は` `知らないと損` `最強` `絶対` `驚愕` `やばい` `話題` |
| **禁止**（煽りの構文）               | 数量煽り（`○つの`）、二人称命令（`〜しよう` `〜すべき`）、最上級・誇張   |
| **許可**（記事主体の視点）           | 引用的枠 `〜と言われた` `〜だと思っていた` `〜ではなかった`              |

引用的枠は**記事の視点であって媒体の主張ではない**ため中立性を侵さない。
最も魅力的な表現はここに集中する。

### 4-3. 目標形の3階層（few-shot の設計根拠）

| 評価       | 例                                                                     | 理由                                                                                                                                      |
| ---------- | ---------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------- |
| **最良**   | `結婚式準備を一人で進める心構え` ｜ `結婚式をしたい人ではなかった`     | 引用的視点・人間の声・結論を完全に伏せる・タイトルと語彙が全く重ならない。**few-shot の筆頭に置く**                                       |
| **良**     | `式場見学で確認すべきポイント` ｜ `館内案内で実際に何が起きているのか` | 場面を名指し、答えを伏せ、タイトルに無い視点を足す。疑問形名詞化は有効な型                                                                |
| **要注意** | `式場マネージャーが語る見積もりの仕組み` ｜ `見積もりが上がること`     | 節の形は良いが**記事の発見（見積もりは上がる）を開示している**＝軽度のゼロクリック化。`見積もりが上がる瞬間はどこか` なら結論を伏せられる |

**「節にすれば良い」ではなく「節で問いを立てる」まで規定しないと、
「〜こと」名詞化は結論漏洩の型に化ける。** この差は規則文だけでは伝わらないため
few-shot が必須である（§4-4-D1）。

### 4-4. 決定事項

#### D1. プロンプトを書き換える（最大の ROI）

- **「体言止め」要求を撤回**し、**「問いを立てる節」**を要求する（H0 の是正）。
- **few-shot を導入する。** 現在ゼロ。形式は `(タイトル, 弱いアンカー, 強いアンカー, なぜ)` の
  **対比型を4組**＋**負例2つ**（タイトルのエコー1つ、煽り1つ）。
  **負例を入れないとモデルは「強い」を「派手」と誤読する。**
- **文字数を目標として明示する**（`18〜36字を目安に。10字台は短すぎる`）。
  median 10字・40字到達0件は、モデルが 40 を上限としてではなく
  **無関係な数字として**扱っている証拠である。
- **gate が許すことを、禁止と同じ声量で「許可」として書く**（萎縮の解消はこの一文が担う）:
  「助詞・接続表現・ひらがなを含む述語や言い換えは自由に使ってよい。
  原文と逐語一致させる必要があるのは、漢字・カタカナの内容語だけ」。

#### D2. gate の「形」を変える（閾値を下げるのではない）

`CONNECTOR_ALLOWLIST` 方式は**原理的に収束しないため廃する**。理由:

1. **列挙は必ず不足する。** 接続表現・言い換え・和語述語は開いたクラス。
2. **LLM は allowlist を知らない。** 拡張しても gate は緩むが萎縮は緩まない。
   `678bcbd` で20語足しても棄却率3.2%のまま淡白なのがその証拠。
3. **リスクの形と一致していない。** 現 gate は次の2つを混同している。
   - **リスクA（本物）**: 記事に無い事実の主張 — 数値・金額・日付・固有名詞・断定的評価
   - **リスクB（無害）**: 原文に literal に無い語 — 言い換え・接続・述語の活用

   現 gate は **B を全力で罰し、A は偶然しか捕まえていない**。実際、
   数値・会場名の禁止は**プロンプト指示だけで機械的検証が存在しない**（§2-6）。
   **本物のリスクが今ノーガードである。** これが「厳しすぎるのに守れていない」の正体。

**置き換え: 文字種による非対称接地**

> **漢字のみ／カタカナのみで構成される2字以上のトークンは、原文に逐語で存在しなければならない。
> ひらがなを含むトークンは接地を要求しない。**

- `銀座` `見積もり` `ホテルウェディング` 等の**内容語＝捏造リスクの本体**は
  ほぼ漢字/カタカナ塊 → 接地を要求。
- `実際に何が起きているのか` `もっと早くやればよかった` `〜ではなかった` 等の
  **述語・接続材＝リスクゼロの表現力**は、ひらがなを含む → 自由。
- **§3-3 のうまくいっている例がちょうど解禁され、捏造だけが締まる。**
- `CONNECTOR_ALLOWLIST` は「漢字のみの機能名詞」（`理由` `背景` `経緯` `決め手`）の
  例外リストとしてのみ残す。**そこは実際に閉じたクラスなので列挙が成立する。**

> **確信度は中〜高。これは机上の規則である。§6 Stage 1 のリプレイで
> 公開77件・棄却95件に対して通過/不通過の変化を実測してから採用すること。**

**「逐語一致という無捏造保証を捨てるのは法務後退では」への応答**: 後退ではなく強化である。
現在保証されているのは「使った語がどこかに出現する」だけで、
**語の組み合わせによる捏造を一切防いでいない**（原文に `30万` と `値引き` があれば
`30万の値引き` は現 gate を通過する）。逐語一致は無捏造保証として既に穴だらけで、
支払っている代償（萎縮＝淡白さ）だけが本物である。

#### D3. 決定的 denylist を新設する（実害の本丸）

allowlist が破綻する理由が、そのまま denylist が成立する理由になる
（**煽り語彙は実質的に閉じたクラスであり、列挙が有効**）。

- 数字（半角/全角/**漢数字**）、通貨記号、`円` `万` `%` `割`、日付表現
- 敬称付き人名・SNS ハンドル（既存 `containsPersonalInfoPattern()` を流用）
- 断定的評価・煽り語（§4-2 の表）

#### D4. 表題との非重複を機械的に強制する

> **アンカーは、タイトルに現れない2字以上の内容語トークンを最低1つ含まなければならない。**

- 既存の `extractFeatureTerms()`（助詞・記号分割）をそのまま流用でき、
  **新しい機械を導入せずに済む**（実装は十数行）。
- **偽陽性の方向が安全である。** この規則で落ちるのは
  「アンカーの内容語がすべてタイトル由来」＝定義上まさに排除したいもの。
- 偽陰性は表記ゆれ由来（`見積り` vs `見積もり`）で発生するが、
  **通過方向の誤り**なので実害は小さい。
- **2-gram 重複率（0.567 等）は gate にしない。** 閾値の意味が言語的に説明できず、
  **「なぜ落ちたか」を LLM に返せない。**
  「タイトルに無い語がゼロです」は再試行指示にそのまま使えるが、
  「重複率が0.72でした」は使えない。**2-gram 比率はオフラインの監視指標に留める。**

#### D5. 失敗時の挙動を「棄却」から「アンカーなしで公開」へ変える

現行の `anchor_ungrounded → dropped` は、**逐語タイトルという主要価値を持つ記事を、
装飾要素の失敗で丸ごと捨てている**。現在3件と少ないので目立たないが、
D2〜D4 で gate を強化した瞬間にこの方針は損失に化ける。

1. **1回だけ再生成**する。失敗理由（「タイトル語のみで構成されています。
   タイトルに無い、本文中の語を1つ以上使ってください」）と**タイトルの語彙リスト**を
   プロンプトに戻す。決定的なフィードバックがあるため高確率で成功する。
2. 2回目も失敗 → **アンカーを null にして記事は公開する**（棄却しない）。
3. **テンプレートへのフォールバックは禁止**（`〜のポイント` 等の機械生成）。
   記事に由来しない媒体の付加であり §10 の趣旨に反する。**空欄は敗北ではなく正直さである。**

#### D6. 長さの下限は3層に分ける

| 層                    | 値                   | 挙動                             |
| --------------------- | -------------------- | -------------------------------- |
| プロンプト（目標）    | **18〜36字**         | **ここが実際に分布を動かす主役** |
| gate（実効下限）      | **12字未満で不合格** | 再生成1回 → だめなら null        |
| zod（バックストップ） | `min(6)`             | 2字ゴミの排除のみ                |

**zod で厳しい下限を課してはならない。** zod 失敗は構造化出力のパースエラーとして扱われ、
有用度判定を含むキュレーション1件を丸ごと落としうる。
**gate の失敗は null へ degrade できるが、zod の失敗は degrade できない** —
この非対称性が層分けの根拠である。

上限 40 は**触らない**（誰も届いていない。max 24。上限は制約になっていない）。

#### D7. 原文の確保 — (a) + (c) を併用する 〔**スコープ外 → `shared_plan/17`**〕

§2-4 の通り、§5.3 は「永続化してはならない」であって「取得してはならない」ではなく、
**discovery 経路は既にそう実装されている**。よって全経路でのフェッチは
**プロジェクト自身の先例に整合し、新たな法務判断を要さない**（robots/TOS は別途）。

> ⚠️ ただし §3-5(4) の通り、**discovery 経路は本番で1件も稼働していない**。
> これは**コード上の先例であって運用上の実績ではない**。
> 「既にやっているから安全」という論法は使えず、
> フェッチ範囲の拡張は**実質的に新規の運用判断**として扱うこと（Stage 0-7 で背景を確認する）。

**D7 は二重に回収される。** §3-5(5) の通り、棄却92件（dropped の 96.8%、
`blog/evergreen` 72件・`blog/google-news` 20件）は
「og:description が空だった」という二値判定だけで捨てられている。
**本文を取得すればこの92件は救済されうる。**
アンカーの改善と、公開母数の回復（77件 → 最大169件）が同じ投資で得られる。

ただし**取得だけでは不十分**である。真の問題は取得ではなく、
**取得したものを捨てた後に gate を再実行できてしまう**ことにある。
現行アーキテクチャは暗黙に「gate のコーパスは DB から再構成できる」と仮定しており、
discovery ではその仮定が既に破れている。`9d7aac0` の事故はこの仮定破れの顕在化である。
**フェッチ範囲を広げれば、同じ事故がすべての経路で起きるようになる。**

- **フェッチ失敗時の挙動が設計の本体である。** 404 / paywall / robots 拒否 /
  タイムアウト時に「タイトルだけで生成する」に落ちたら、今と同じ劣化を新経路で再生産する。
  **失敗＝アンカー生成をスキップ（null のまま、記事は公開）が唯一の正解。**
- **google-news 経路は割り切る。** リダイレクタ経由で取得先が不安定であり、
  費用対効果が明確に低い。「アンカーを生成しない」で運用する。
- **evergreen（og:description 1文）も同様に、改善ではなく
  「アンカーを外す」が正解の可能性が高い**（Stage 0 の層別結果で判断する）。

**副次効果**: D4（表題非重複）を入れると、**コーパス貧弱の自動検出器としても機能する**。
コーパス＝タイトルのとき「原文に接地」と「タイトルに無い語を含む」は**同時に充足不能**になり、
2つの gate の連立が「材料が足りない」を機械的に自白させる。
別途の長さ閾値より頑健である。

#### D8. 判定メタデータを記録し、劣化を構造的に禁止する 〔**スコープ外 → `shared_plan/17`**〕

本文そのものは保存しない（**ハッシュと長さのみ**）ので §5.3 に抵触しない。

- `grounding_source`: `full_body` / `rss_excerpt` / `og_description` / `title_only`
- `corpus_length` / `corpus_hash` / `prompt_version` / `grounded_at`

その上で不変条件を課す:

> **判定済みのアンカーを、より貧弱なコーパスで再判定・再生成してはならない。**
> `title_only` で `full_body` 生成のアンカーを上書きしようとしたら、それは例外にすべき事象である。

これが入れば **H2 の事故クラスは恒久的に閉じる。gate の閾値をいくら調整しても閉じない。**

> ⚠️ **要確認**: spec に「`ALTER TABLE` 不可の制約」への言及がある（§10-3 の `aiTitle` 休眠カラムの件）。
> `tests/migrations-additive.test.ts` の存在から追加方向のマイグレーションは可能と推測されるが、
> **Stage 0 で実際の可否を確認してから D8 の実装方式を確定する**こと。
> 不可の場合は既存の休眠カラムの再利用か、別テーブルへの記録を検討する。

#### D9. backfill の劣化経路を塞ぐ（**D9-min のみ本プラン。完全形は `shared_plan/17`**）

> **backfill でも同じフェッチを行う。行わないなら、backfill は topicAnchor に触れてはならない。中間は無い。**

**本プラン（16）はフェッチを含まない（D-O1）。したがって後段を採る:**

> **D9-min: backfill は、照合コーパスがタイトルのみになるレコードの
> `topicAnchor` を再生成してはならない。** 該当レコードは既存アンカーを保持したままスキップする。
> 判定は**出力を見てからではなく、生成前に入力を見て**行う（preflight）。

これは `9d7aac0` の safe-filter の置き換えであり、数行で実装できる。

backfill が DB の `original_excerpt` を近道として使う限り、`9d7aac0` と同じ劣化を必ず再生産する。
backfill は「キュレーションパイプラインの再実行」であって「DB 内の値の再計算」ではない。

**`9d7aac0` の safe-filter は無効なだけでなく有害である。**
「安全弁がある」という誤った安心を作り、劣化を無検知にした。
**安全弁を出力側（postflight）に置いたのが設計ミスで、
正しくは入力側（preflight: コーパスが貧弱なら生成しない）である。**

**`CURATION_PROMPT_VERSION` の bump は「プロンプト契約が変わった」という事実の記録であって、
再生成の実行トリガーにしてはならない。** 今回の事故は
「バージョンが変わった → 全件再生成」が無条件に走ったことで起きている。正しくは:

> 再生成の対象条件 = `prompt_version < 現行` **かつ**
> `再生成時のコーパスが、既存アンカー生成時のコーパス以上に豊か`

後半の条件が今回欠けていた。**これを backfill のクエリ条件に構造として組み込めば、判断ミスの余地が消える。**

#### D10. spec と実装の乖離を是正する（§2-6）

- §10-3 の「体言止め」要求を D1 に合わせて改定する（H0 の是正）。
- 「zod refine が数字を拒否する」記述を実態に合わせるか、D3 で実装を spec に合わせる。
  **どちらに寄せるかを明示的に決め、経緯を spec に残す。**
- grounding の照合先が「本文」ではなく経路により異なる事実（§2-3）を spec に反映する。

| 手                                                               | 理由                                                                                                                                                                                                                                                  |
| ---------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **形態素解析器（kuromoji / MeCab）の導入**                       | 最も誘惑の強い筋悪手。問題はトークン化精度ではなく**コーパスの貧困と規則の形**であり、解析器はどちらも解決しない。D2 の文字種ヒューリスティックがゼロ依存で便益の大半を回収する。導入判断は「リプレイ計測でトークン化が律速だと示されたとき」まで保留 |
| **LLM に自己検証させる**（2段目呼び出し）                        | 生成器と誤りが相関し、非決定的、監査不能。**法務ポジションの根拠が「機械的に検証している」ことである以上、検証は決定的でなければ意味を持たない**                                                                                                      |
| **gate の全廃**                                                  | gate の**形**が間違っているのであって存在が間違っているのではない。緩和と廃止を混同しない                                                                                                                                                             |
| **`CONNECTOR_ALLOWLIST` にさらに語を足す**                       | 今回もう一度やれば3回目。§4-4-D2 の3点により原理的に収束しない                                                                                                                                                                                        |
| **`max` を 40 から伸ばす**                                       | 誰も届いていない（max 24）。上限は制約になっていない                                                                                                                                                                                                  |
| **リプレイ基盤ができる前に「念のためもう一度 backfill」**        | 同じ事故を同じ理由でもう一度起こす最短経路                                                                                                                                                                                                            |
| **無アンカー時のテンプレート文言フォールバック**                 | 記事に由来しない媒体生成テキストであり §10 の趣旨違反。**空欄は敗北ではなく正直さ**                                                                                                                                                                   |
| **gate のために取得本文を DB に保存する**（「照合用だから」）    | §5.3 の明確な違反。保存してよいのはハッシュ・長さ・出自ラベル・判定結果のみ                                                                                                                                                                           |
| **LLM が見るコーパスを gate のコーパスより広くする**             | 現在の discovery（LLM は先頭1500字、gate は全文）は**正しい向き**（gate の方が寛容）なので維持。逆向きにすると萎縮が構造化される                                                                                                                      |
| **UI ラベル短縮のついでに `USEFULNESS_LABELS` を「共通化」する** | `shared_plan/15` §4-2 の判断を維持。`rationale_text` の長さが全件変わりテストと backfill が巻き添えになる                                                                                                                                             |

## 6. 実行計画

**大原則: 全件再生成は当面やらない。** 順序は
**計測 → 可逆性の確保 → 入力の修復 → コホート別展開**。
`shared_plan/15` の D5（全件再生成）は本プランで**撤回**する（§8 参照）。

### Stage 0: 計測と前提確認

**大部分は本プラン作成時点で実施済み（§3-5）。残る未確認事項のみを先に潰す。**

| #   | 項目                                                                      | 状態                                             |
| --- | ------------------------------------------------------------------------- | ------------------------------------------------ |
| 1   | 重複率の層別（H0 vs H1 の決着）                                           | ✅ 完了 — §3-5(1)。**H0 が主因**と確定           |
| 2   | 「節 vs 裸の名詞句」の分布                                                | ✅ 完了 — §3-5(2)。H0 の直接証拠                 |

**完了判定**: 5〜7 が判明していること。

### Stage 1: オフライン・リプレイ基盤（`@fixer`）

**本番 DB に一切触れない。** 新プロンプト＋新 gate を既存177件に適用し、旧 vs 新を差分表示する。

指標: 文字数分布 / タイトル新規トークン数 / 2-gram 重複率 / gate 判定内訳 / 無アンカー率。

**同時に、現行の公開77件が新 novelty gate（D4）を何件通過するかを測る。**
§3-1 の 44% が落ちる見込みであり、**その事実を先に見てから閾値を決める。**

**D2（文字種による非対称接地）は机上の規則である。ここで公開77件・棄却95件に
リプレイして通過/不通過の変化を実測するまで、採用を確定しない。**

### Stage 2: プロンプトと gate の改訂（`@fixer`）

- D1（プロンプト: 体言止め撤回・few-shot・文字数目標・許可の明記）
- D2（文字種による非対称接地）／ D3（denylist）／ D4（表題非重複）／ D6（長さ3層）
- D5（失敗時は棄却せず null へ degrade、再生成1回）
- 関連テストの追随（**テストの実装は `@fixer`、実行と判定は Orchestrator**）

Stage 1 のリプレイ結果と矛盾する変更は入れない。

### Stage 3: 検証ゲート（Orchestrator が実行）

`lint` / `type-check` / `test` / coverage tiers / spec-refs / security / smoke test。

**新設した gate は、意図的に壊して「実際に落ちること」を確認するまで完了と見なさない**
（AGENTS.md「ゲートが緑であることと、ゲートが機能していることは別である」）。
具体的には D3 の denylist に数値入りアンカーを、D4 にタイトルのエコーを食わせて落ちることを確認する。

### Stage 4: 可逆性の確保（`@fixer` → Orchestrator が確認）

`topic_anchor_prev` 相当のスナップショットを取る。
**`9d7aac0` が不可逆に見えることが今回の最大の教訓であり、
次の backfill が可逆でないなら実行してはならない。**

### Stage 5: backfill の劣化経路を塞ぐ（`@fixer`）

D9-min のみ。`9d7aac0` の safe-filter（postflight）を
**preflight（コーパスがタイトルのみなら生成しない）**に置き換える。

**ここが直る前に `CURATION_PROMPT_VERSION` を bump してはならない。
順序を逆にすると、劣化を新バージョンの名前で再生産する。**

D7（フェッチ）・D8（メタデータ）・D9 完全形は `shared_plan/17` へ（D-O1）。

### Stage 6: コホート順の展開（Orchestrator）

**全件再生成はしない。** `CURATION_PROMPT_VERSION` を bump した上で、
**コーパスが薄いレコードは D9-min により自動的に対象外**になる。

| 順  | コホート                                                    | 方針                                                                                    |
| --- | ----------------------------------------------------------- | --------------------------------------------------------------------------------------- |
| ①   | `blog/note`（59件・excerpt 実在）                           | 最初に流す。母数が最大で材料もある                                                      |
| ②   | `blog/evergreen` / `blog/google-news`（18件・excerpt NULL） | D9-min によりスキップされる。**17 でフェッチを入れるまでアンカーは現状維持または null** |

**①の最初の10〜20件を人間が目視してから残りを流す。**

### Stage 7: spec の改定（`@fixer`）

D10。§10-3 の体言止め要求の改定、数値禁止の乖離是正、grounding 照合先の実態反映。
**改定理由と経緯を spec 本文に残す**（§10 の改訂履歴の様式に従う）。

### Stage 8: 目視確認とコピーの最終調整（Orchestrator）

375px / 320px / デスクトップでフィード全体を確認。
`@designer` の視覚・操作の意図を保ったまま、Orchestrator が文言を最終確認する。
