## 1. 発端

オーナーの要求(要約):

> 18・19 が実装された後の姿を前提に、フィード表示を「モダンでポピュラーなフロントエンドの見せ方」に刷新したい。
> 関心は特に各パネルの表題・要約・タグの見せ方。3案を検討し、1案を最終案として推奨・詳細化してほしい。

## 2. 前提として確定させる「実装後のカード」の姿

18・19 の実装が完了した時点で、フィードカードが受け取れるデータは次の形になる(オーナー指示の再掲・本プランでの確認事項)。

| フィールド      | 型                    | 表示上の扱い                                   |
| --------------- | --------------------- | ---------------------------------------------- |
| `originalTitle` | `string`              | 逐語。改変・要約・言い換え禁止(法務不変)       |
| `topicAnchor`   | `string \| null`      | ≤40字の判定根拠アンカー。要約ではない          |
| `topics`        | `string[]`(18 で新規) | AI 自由選定 2〜4 個、各2〜10字。欠損時は空配列 |
| `category`      | `Category`(11種)      | 固定列挙                                       |
| `sourceName`    | `string`              | 常時表示(著作権上必須)                         |
| `author`        | `string \| null`      | 非 null なら必ずクレジット表示(著作権上必須)   |
| `publishedAt`   | `string`              | 相対時刻表示(既存 `PublishedTime`)             |
| 元記事 URL      | —                     | 最優先 CTA(著作権上必須)                       |

削除される(19 で消える): `usefulness` 型そのもの、trend/classic バッジの UI 露出、`feed-lane-trend.tsx`。
フィードは単一レーン1本。

存在するが表示しない: `aiSummary`, `rationaleText`, 有用度スコア(spec §9.8 でスコアの UI 表示は禁止)。

掲載順: 有用度スコア降順 → publishedAt 降順 → id 降順(固定、本プランでは変更しない)。

法務不変部分(spec.md §10・§11、緩めない):

- 記事本文を一切生成・永続化しない。`originalExcerpt` は常に null。
- タイトルは逐語。UI 層で言い換え・装飾的改変をしない。
- **外部サイト画像の再掲載・描画は全面禁止**。OGP サムネイルは使えない。ビジュアル訴求は画像に頼れない。
- 結論・結果・具体的数値の開示禁止。
- `sourceName` 常時表示、`author` は判明時必ず表示。
- トピックタグは AI 自動判定である旨の恒常的な開示注記が必須(フィードヘッダ直下に1行、フッター不可)。
- タグ・アンカーを「根拠文」として提示しているように見せる構造にしない(視覚的・構造的に分離)。

## 3. 現状の負債(是正対象)

- `feed-card.tsx` のタイトル/本文サイズが `text-[17px]` `text-[15px]` `text-[14px]` `text-[12px]` `text-[11px]` の
  任意値だらけで、統一されたタイポスケールが存在しない。
- `variant: "visual" | "editorial"` の2系統分岐は 19 でレーンが1本になった時点で存在意義を失う。
- `--color-trend` / `--color-on-trend` / `--trend-tint-*` は 19 実装後に用途を失う(バッジ・空状態・ボタン
  variant で使用中、`badge.tsx` の `variant="trend"`、`button` の `variant="trend"`、`empty-state.tsx` の
  グラデーション、いずれも参照が残る)。
- `rounded-2xl` + `shadow-card`(二重の box-shadow)は、外部調査(librarian 済み)で「2026 に古く見える」代表格
  として名指しされている。

## 4. 外部調査の要旨(librarian 済み、本プランでの前提として採用)

- タイトルは2行クランプが事実上の標準(現状3行)。ウェイト差で階層。リンク下線は hover のみ。
  出典は favicon 16px + ドメイン名(www 除去)を小さくグレーで。
- 要約は2〜3行クランプ + タイトルより一段トーンを落としたグレーで常時表示が主流(hover 展開はモバイルと相性が悪い)。
- タグは「静的要素と対話型要素が同じ見た目を共有すると混乱を招く」原則。押せないタグを強いフィルド pill に
  してはいけない。ニュートラルなアウトライン/セカンダリ + アクセント1色が2026の主流。カテゴリ11種の色分けは
  種類過多で破綻する(4〜6種までが目安)。カードあたり2〜3個表示 + `+N` 省略が定石。
- 均質な情報単位が大量に並ぶフィードには単一カラム高密度リストが最適。Bento はランディング向けでフィードとは
  本質的にミスマッチ。
- 2026 に古く見える意匠: 強い drop shadow、過度な角丸(2xl 多用)、グラデーション多用。主流は
  hairline border + ニュートラルグレースケール + アクセント1色希少使用(Vercel Geist / Linear)。
- デジタル庁デザインシステムβ版の和文タイポ指針: 行間は本文150〜170%・見出し140%・UI 100%、字間は
  0 / 0.01em / 0.02em、フォントサイズは本文16〜18px・中見出し20〜36px・補足14px。
- line-clamp は SR/検索でクランプ部が扱いにくいため `title` 属性や `aria-label` で全文を保持するのが望ましい。

**この案件固有の制約**: 外部画像を一切再掲載できないため、B案(エディトリアル型)がサムネイルを前提とする
一般形のままでは成立しない。文字だけでどう品位を作るかが全案共通の論点になる。

## 5. 3案の比較

### 案 A: 高密度リスト型(Techmeme 系)

**概要**: 1行〜2行の情報単位を縦に密に積む。カードというより「行」に近い。区切りは hairline border のみ、
box-shadow なし。視覚的な主役はタイトルのテキストそのもの。

**ワイヤーフレーム**:

```
┌─────────────────────────────────────────────┐
│ 衣装・ドレス                          note・鈴木花子・3時間前 │
│ 二次会ドレスを式当日と同じにしない理由を考えてみた            │
│ 費用面と「特別感」の両立という判断軸に言及           →  │
│ #費用感覚 #写真映え #ゲスト目線                              │
├─────────────────────────────────────────────┤
│ 会場・装花                              google-news・5時間前 │
│ 会場装花を持ち帰る文化、実は地域差が大きい               │
│ ...
```

**表題**: 2行クランプ、`font-semibold`、サイズは本文よりわずかに大きい程度(過度な強調をしない)。
**要約(topicAnchor)**: タイトル直下1行、grayトーン、1行クランプ。null なら要素ごと非表示。
**タグ**: 最下段にテキストのみ(`#語`)、アウトラインすらなし。押せないことが形からも明白。

**長所**: 実装コストが最小。1画面あたりの情報量が最大化され「量をさばくフィード」という実態に最も忠実。
外部画像なし制約と自然に整合(そもそも画像枠を持たない設計だから欠落感がない)。
**短所**: 単調になりやすく「モダンでポピュラー」という語感からは地味寄りに振れる。カード同士の境界が薄いため
タップ領域の誤操作(隣の記事に触れる)対策が要る。ブランド感・エディトリアルな品位は出しにくい。
**実装コスト**: 低。既存 `feed-card.tsx` の大幅な削ぎ落としで足りる。
**法務適合**: 適合。要素が少ない分、逐語・非改変の担保もしやすい。

### 案 B: エディトリアル型(サムネイル前提の再設計)

**概要**: 雑誌の記事一覧のような、ゆとりのあるカード。通常はサムネイル画像が主役になるが、本プロジェクトは
外部画像を使えないため、**画像枠の代わりにカテゴリ由来のタイポグラフィ装飾**(大きめの飾り文字、または
カテゴリ名を縦組み風に配置する等)で「絵のかわり」を作る案。

**ワイヤーフレーム**:

```
┌───────────┬─────────────────────────────┐
│ 衣装      │ 二次会ドレスを式当日と        │
│ ・        │ 同じにしない理由を考えてみた   │
│ ドレス    │                               │
│ (装飾文字) │ 費用面と「特別感」の両立という…│
│           │ #費用感覚 #写真映え #ゲスト目線 │
│           │ note ・ 鈴木花子 ・ 3時間前    │
└───────────┴─────────────────────────────┘
```

**表題**: 2行クランプ、大きめサイズ、セリフ系ディスプレイ書体(既存 Fraunces の路線を継続)で「読み物」感を強調。
**要約**: タイトル下、2行クランプ、通常の本文トーン。
**タグ**: カード下部、アウトライン pill 2〜3個。

**長所**: 「紙と朱」という既存コンセプトの正当な発展形になり得る。文字だけでも装飾ブロックがあることで
視覚的なリズムが単調にならない。
**短所**: 装飾ブロックが「本物の記事に紐づく画像」であるかのように誤読される危険がある。カテゴリ由来の
飾り文字だけでは11種の情報量を安定して支えきれず、代わり映えのしないパターンの繰り返しになりやすい
(4〜6色までが目安という調査知見と、カテゴリ11種という現実の板挟み)。カード高さが嵩み1画面の情報密度が
案Aより明確に落ちる。実装コストも装飾ブロックの分だけ増える。
**実装コスト**: 中〜高。装飾ブロックのバリエーション設計が実質的な新規デザインタスクになる。
**法務適合**: 装飾ブロックが実際の記事内容を暗示しない(=本文由来の絵ではなくカテゴリラベルの再表現に
留める)よう設計すれば適合するが、誤読リスクの管理コストがA・Cより高い。

### 案 C: Bento・マガジン型

**概要**: カードサイズを記事の目立たせ方に応じて可変にする(2×1の大型カード + 1×1の通常カードを混在)。

**長所**: ランディングページ的な華やかさは出せる。
**短所**: librarian 調査で「Bento はランディング向けでフィードには本質的にミスマッチ」と明確に指摘済み。
均質な情報単位(記事)を不均質なサイズで並べる根拠が本プロジェクトには存在しない(どの記事を「大きく」
扱うかの基準がない — 有用度スコアを可視化すると spec §9.8 のスコア非表示制約に抵触する)。無限スクロールの
フィードとの相性も悪い(スクロール中にレイアウトの疎密が変わり続けると視線誘導が破綻する)。
**実装コスト**: 高(グリッドの動的な段組みロジックが必要)。
**法務適合**: 大型カードの選定基準がスコア非公開の制約と衝突しやすく、設計として無理がある。

**結論**: 案Cはこの時点で不採用とする(調査知見・法務制約の両面で積極的な採用理由がない)。

### 案 D(追加提案): 高密度リスト + 最小限のカード分離(A と B のハイブリッド)

librarian の3方向をそのまま適用すると A は地味に振れすぎ、B は画像なし制約と正面衝突する。そこで
「案A の情報密度と正直さ」を土台にしつつ、「案B の可読性(カードとしての呼吸)」を薄く足す第4案を設計判断
として追加する。

**概要**: 案Aの1カラム・高密度は維持しつつ、行と行の間に薄い区切りではなくカード単位の余白(hairline border

- わずかな background 差)を与え、タップ領域とスキャン単位を明確化する。装飾ブロックは持たない(画像なし
  制約を無理に埋めようとしない)。かわりに、カテゴリ名を先頭に置く控えめなアイコン+テキストのラベルで
  視覚的な起点を作る(装飾ではなく機能ラベルとして扱う)。

**長所**: 画像なし制約に対して「ないものを無理に作らない」という誠実な解決になる。実装コストは案Aに近い
低さを保ちながら、案Aの単調さを緩和できる。
**短所**: 案A・Bの中間的な性格ゆえ、強い個性という点では両者に一歩譲る。

**判断**: 3案の比較としては A/B/C を提示するが、**最終推奨は案Aをベースに調整を加えた D とする**。
以降の詳細化は D を最終案として記述する。

## 6. 最終案(案 D)の詳細化

### 6-1. タイポグラフィスケール

`@theme inline` に役割ベースのトークンを追加する(現状の `text-[Npx]` 任意値を全廃)。

| トークン名      | px   | line-height                 | letter-spacing                  | 用途                | デジタル庁指針との対応                                                                                                                                                                                                       |
| --------------- | ---- | --------------------------- | ------------------------------- | ------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `--text-title`  | 17px | `--leading-jp-heading`(1.5) | `--tracking-jp-heading`(0.01em) | カードタイトル      | 中見出し下限(20〜36px)よりやや小さいが、フィード内の密度優先で本文上限に近い値を採用(判断根拠: 設計判断。指針は「中見出し」を単独の大見出しとして想定しており、リスト内タイトルは指針のUIコンポーネント区分に近いと解釈した) |
| `--text-anchor` | 14px | 1.6                         | `--tracking-jp-body`(0.03em)    | topicAnchor(要約枠) | 補足(14px)に一致                                                                                                                                                                                                             |
| `--text-meta`   | 13px | 1.5                         | 0                               | 出典・日時・タグ    | UI コンポーネント(100%)寄りにやや緩め、指針の「補足」よりわずかに小さいが可読性下限として妥当と判断(設計判断)                                                                                                                |
| `--text-badge`  | 12px | 1                           | 0.02em                          | カテゴリバッジ      | UIコンポーネント区分(letter-spacing 0.02em)に一致                                                                                                                                                                            |

根拠の区分: `--text-anchor` はデジタル庁指針の「補足14px」に直接対応(調査根拠)。`--text-title` と
`--text-meta` は指針の区分がリスト形式のフィードカードを直接想定していないため、密度優先で調整した
設計判断であることを明記する。`--text-title` を本文上限相当に抑えるのは、案Dが「高密度リスト」である以上
タイトルを見出し的に肥大化させると1画面の情報量が落ちるため(本プロジェクト固有の判断)。

body 側の本来の本文サイズ(16〜18px)は本プロジェクトではフィードカードに地の文本文を持たない
(originalExcerpt は常に null)ため未使用。ただし将来的にヘッダ注記等で使う場合の指針として
`--text-body: 16px` も予約しておく。

### 6-2. カラートークンの再設計

**方針**: `--color-trend` を廃止し、アクセント色は**1色に絞る**(既存の朱を継続採用)。カテゴリ11種は
**色分けしない**。

根拠:

- librarian 調査: カテゴリ別カラーコーディングは4〜6種までなら有効、11種では破綻する。本プロジェクトの
  `CATEGORIES` は11種で固定(`src/lib/types.ts`)であり、削減や再編は本プランのスコープ外(spec 変更を伴う)。
  よって色分けという手段自体を採らないのが妥当。
- 2026の主流(Vercel Geist / Linear)は「ニュートラルグレースケール + アクセント1色を希少使用」。カテゴリを
  グレースケールのアウトラインバッジに統一し、アクセント色は CTA(原文を読むボタン)とフォーカスリングにのみ
  使う設計に寄せる。
- 既存コンセプト「紙と朱」(globals.css:8-12 のコメント)は**継続を推奨**する。朱をアクセント1色として残す
  ことは、19 で trend バッジという「用途」を失っても、色そのものを CTA/フォーカスリングという新しい用途に
  転用すれば成立する。ゼロから配色し直すコストとブランド連続性を天秤にかけた設計判断。ただし最終可否は
  §7 未決事項に諮る。

再設計後のトークン(`globals.css` `:root` / `.dark` / `@theme inline` を想定、値は暫定):

```
--surface / --surface-hover / --border / --ring: 維持(すでにニュートラル)
--accent: var(--trend) の値を継承(#b33a24 系) — CTA ボタン・フォーカスリング・選択状態のみに使用
--on-accent: 既存 --on-trend を継承
--ai-chip 系: 維持(AI開示バッジという役割は変わらず残る。§6-6 参照)
```

廃止: `--trend-tint-a` / `--trend-tint-b`(空状態のグラデーションで使用中 → 空状態自体もニュートラル化。
§6-9 参照)、`--classic` / `--on-classic` / `--classic-tint-*`(19 でバッジ用途消滅、代替用途なし)。

カテゴリバッジは既存の `variant="category"`(アウトライン、ニュートラルグレー)をそのまま踏襲する
— これは意図せず既に「2026の主流」に合致していた箇所であり、変更不要。

### 6-3. 表題(タイトル)

- クランプ: 2行(現状3行から変更)。
- サイズ/ウェイト: `--text-title`(17px)、`font-semibold`。フォントは `font-display`(Fraunces + 和文
  明朝フォールバック)を維持 — セリフ系の質感が「エディトリアルだが高密度」という案Dの性格と合う。
- リンク affordance: カード全体をクリック可能領域にしつつ、下線は hover 時のみ付与(Techmeme の判断を踏襲)。
  タイトル自体は `<a>` でラップし、フォーカスリングは `--ring` トークンで可視化する。
- 出典表示: タイトル直下ではなくフッターに集約する既存構成を維持し、**ドメイン名(www 除去)のテキスト表示**を
  基本形とする。favicon 16px の併記は**保留**(§9-3)。
  保留の理由: favicon は記事本体の画像ではないが、(a) 外部ホストへの画像リクエストが閲覧者ごとに発生し
  spec §11 のアクセス規律との整合を確認していない、(b) Google の favicon サービス等を経由すると閲覧者の
  IP が第三者に渡る、(c) 静的マッピングにすると新規ホスト追加のたびに保守が要る。
  **確認が取れるまでは favicon なしで成立する設計**とする(Techmeme もファビコンを持たずドメイン名のみで
  20年運用している)。
- **逐語制約の UI 担保**: `Title` コンポーネントの props を `{ title: string }` ではなく
  `{ originalTitle: FeedCardData["originalTitle"] }` のように**型でフィールド名を固定**し、コンポーネント内で
  一切の文字列加工(トリム・省略記号付与以外の変換)を行わない。具体的には、タイトル文字列を受け取って
  `.replace()` 等の変換を適用する処理をコンポーネント内に書くこと自体を禁止するコードコメントを付す
  (機械的な型強制はできないため、レビュー規律として明文化する)。line-clamp による視覚上の省略は文字列の
  改変ではなくCSSでの表示制御であるため許容する。

### 6-4. 要約(topicAnchor)

- 表示位置: タイトル直下、1行(現状の `line-clamp-1` を維持)。
- クランプ: 1行。案Aの高密度方針を踏襲し2〜3行クランプは採らない(topicAnchor は元々≤40字であり複数行を
  要しない)。
- トーン: `--text-anchor` サイズ、`--color-muted-foreground`。タイトルより明確に一段トーンを落とす。
- null 時の挙動: 要素ごと非表示(プレースホルダ・スケルトンは出さない、というのは18の設計を踏襲)。
  **カード高さの扱い**: 高さは揃えない(要約が無い記事はその分カードが低くなることを許容する)。理由:
  高さを固定するために空白を埋めると「本来ないはずの情報」があるかのような視覚的圧力を生み、
  「記事本文ではない」ことの誠実さと矛盾する。高密度リストという構成上、カード高さの不揃いは
  他の情報単位との比較を妨げるほどの実害を持たない(1行分の差でしかない)。
- 「本文ではない」ことの視覚的誠実さ: topicAnchor には見出し語(「要約」「サマリー」等)を一切付けない。
  タイトルとの間に十分な行間を取り、書体もタイトル(明朝系)とは変えてゴシック系にすることで「別の情報種別」
  であることを構造的に示す。

### 6-5. タグ(topics 2〜4個)

- 視覚形式: **テキストのみ**(`#語` 形式、背景色なし、枠線なし)。librarian の原則
  「静的要素と対話型要素が同じ見た目を共有すると混乱を招く」を最も厳密に満たす形式として採用。
  カテゴリバッジ(アウトライン pill、押せる CTA と誤認されない程度の弱い枠)とは明確に階層を分ける
  — カテゴリは「分類」という構造的情報なのでバッジ形状を維持、topics は「参考ラベル」なのでバッジ形状すら
  与えない。
- 非対話性の示し方: `cursor: default`、hover 時の視覚変化なし、`<span>` で実装し `<button>` `<a>` を使わない。
- `+N` の要否: **不要**。topics は元々2〜4個という上限が18で確定しており、`+N` 省略が要るほどの数にならない。
  4個全て表示する。
- カード内バッジ総数の上限方針: **カテゴリバッジ1個 + topics 最大4個 = 最大5個**。18が懸念していた
  「最大6バッジで情報密度が破綻するリスク」は、19でtrend/classicバッジが消滅する分そのまま1個減る形で
  解消される。ただし5個でも「バッジ」として並べると密度過多になるため、**topics はバッジではなくテキスト
  タグ列とすることで視覚的な「個数」の圧を下げる**(バッジ形状は枠線・背景・padding を持つため4個並ぶと
  重いが、テキスト+区切り記号なら同じ4語でも軽く見える)。カテゴリバッジ(1個・アウトライン形状)のみを
  「バッジ」として残し、topics は「タグ行」という別カテゴリのUI要素として扱うことで、視覚的な総数上限の
  問題自体を回避する設計とする。

### 6-6. AI 自動判定の開示

- フィードヘッダ直下の恒常注記(暫定文言、オーナー確認前提):
  「カテゴリとトピックタグは、AI が記事の内容から自動で判定しています。誤りを含む場合があります。」
  ※ `category` も AI 判定の産物であり、注記が topics だけを対象にしていると開示範囲が実態より狭くなる。
  18 の原案(「カテゴリ・トピックはAIが自動判定しています。誤りを含む場合があります」)と対象範囲を揃えた。
- 位置: `page.tsx` のフィード見出しの直下、フィード本体の直前に1行、`--text-meta` サイズ・
  `--color-muted-foreground` で控えめに配置。
- タグコンテナの属性: タグ行全体を `<ul aria-label="AIが自動選定したトピック">` 等でラップし、
  各タグ `<li>` には `title` 属性は付けない(タグ語自体がテキストとして既に読み上げ可能なため冗長)。
  ただしタグ行コンテナには `title="AI による自動判定。誤りを含む場合があります"` を付与し、hover 時の
  補助説明とする(ヘッダ注記と語を揃える)。

### 6-7. カード全体のレイアウト

- 単一レーン化後、グリッドは1カラム(モバイル)〜必要に応じて2カラム(広い画面、`sm:grid-cols-2` 等)を
  検討可とするが、案Dの「高密度リスト」という性格上、**1カラム基本**を推奨する(2カラムにすると1行あたりの
  文字数が減りタイトル2行クランプとの相性が悪化するため)。最終判断は実装時のビューポート幅の実測に委ねる。
- 余白: `p-4` 相当を維持しつつ `gap-2.5`(現状 editorial 系の値に統一、visual/editorial の分岐そのものを廃止)。
- 境界線 vs シャドウ: **hairline border(`border border-[var(--color-border)]`)のみを採用し、box-shadow
  (`shadow-card`)は廃止**。調査知見(2026に古く見える意匠として強い drop shadow が名指しされている)に
  加え、`--surface` と `--background` の色差だけでカード面を識別できるため shadow の必要性が薄い。
- 角丸: `rounded-2xl` → `rounded-lg` 程度に縮小(過度な角丸も同じ調査知見で名指しされている)。
- hover/focus: hover はタイトル下線 + `background: var(--surface-hover)` のわずかな変化のみ。focus は
  `--ring` トークンによる可視フォーカスリングをカード全体(または内包する `<a>`)に付与。
- 出現アニメーション: 既存の `motion-safe:animate-in fade-in slide-in-from-bottom-2` は**残す**
  (「1つの良いタイミングのアニメーション」という設計原則に合致しており、単一レーン化後も違和感がない)。

### 6-8. アクセシビリティ

- セマンティクス: `<article>` を維持。見出しレベルは `<h3>`(フィード全体の `<h2>` 配下として)。
  タグ列は `<ul role="list"><li>`(role="list" は Safari の VoiceOver がデフォルトの list role を
  スタイル指定時に落とす既知の挙動への対策として付与)。
- コントラスト比: `--text-meta`(13px、グレー)は WCAG AA(4.5:1、小文字は3:1ではなく4.5:1が必要)を満たす
  グレー値であることを実装時に検証する(現状の `--muted-foreground` の値が既にそれを満たしているかは
  未検証 — 実装 Stage の完了条件に含める)。
- フォーカスリング: カードリンク・CTAボタンいずれも `--ring` で可視化、`outline-offset` を確保。
- タップ領域: カード全体を実質的なタップ領域とする(カード内の複数リンクが入れ子にならないよう、外部リンクは
  CTAボタンに集約し、タイトルリンクとCTAボタンの2箇所のみをフォーカス可能要素とする)。
- `prefers-reduced-motion`: `motion-safe:` prefix により既に対応済み(tw-animate-css の挙動を踏襲)。

### 6-9. 空状態・ローディング

- `empty-state.tsx`: 現状 `variant: "visual" | "editorial"` の分岐を持つが、単一レーン化後は不要になる
  (19のスコープでもあるため重複するが、本プランとしても表示刷新の一部として明記する)。グラデーション
  背景(`--color-trend-tint-a/b` 由来)はトークン廃止に伴いニュートラルな `--surface-hover` 系の単色に置換。
- skeleton: `--color-skeleton` トークンは維持。カードのスケルトンはタイトル2行分 + メタ情報1行分の
  グレーブロックとし、topicAnchor 分のスケルトンは持たない(null 時に非表示という実カードの挙動と一致させ、
  スケルトンが「必ず要約が出る」という誤った期待を生まないようにする)。

## 9. 未決事項(オーナー判断が必要)

1. **和文Webフォント導入の是非**: 現状は意図的に非同梱(システムフォント依存)。本プランはこの判断を
   **維持する**前提で設計した。
   確認済み(`globals.css:105-106`): `--font-display` は `Fraunces → Hiragino Mincho ProN → Yu Mincho → serif`、
   `--font-sans` は `Hiragino Kaku Gothic ProN → Yu Gothic → Noto Sans JP → sans-serif`。つまり
   **案Dの「タイトル=明朝 / 要約・タグ=ゴシック」という書体の描き分けは、和文Webフォントなしで既に成立する**。
   残るリスクは環境差: Windows の游明朝は 17px 前後で線が細く沈みやすく、Android / 一部 Linux には和文明朝が
   無いため generic `serif` にフォールバックして描画品質が読めない。
   選択肢は (a) 現状維持し環境差を許容、(b) タイトルもゴシックに統一して環境差を消す、
   (c) 和文明朝の Webフォントを同梱(重量とのトレードオフ)。オーナー判断を仰ぐ。
2. **既存「紙と朱」コンセプトの継続可否**: 本プランは継続(朱をアクセント1色として存続)を推奨したが、
   19で trend/classic の対比構造が消える以上、朱単色に「情緒的な意味」が残るのか(単なる装飾色に
   なっていないか)はオーナーの美意識判断に委ねる部分が大きい。ゼロベースでニュートラル配色に振り切る
   選択肢も残る。
3. **favicon 表示の可否**: §6-3 では保留とし、ドメイン名テキストのみで成立する設計にした。採用するなら
   spec §11 のアクセス規律との整合(閲覧者ごとの外部画像リクエスト、第三者への IP 露出)を先に確認する必要が
   ある。未確認のまま実装 Stage に進めない。
4. **開示注記の文言**: §6-6 の文言は暫定。法務・トーンの両面でオーナー確認前提。
5. **カードのグリッド段組み**(1カラム固定 vs 広画面2カラム): §6-7 で1カラム推奨としたが最終判断は
   実装時のビューポート実測に委ねるとした部分。デザインとして先に確定させたい場合はオーナー判断が要る。
