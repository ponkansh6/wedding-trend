## 1. なぜこれが必要か

plan 03 の V0/V1 で判明した根本課題:

- 定番レーン（`sourceType: "blog"`）は全 `posts` を有用度スコア順に表示するが、ゲート `ceremonyDecision && !preDecisionOrPhotoShoot` は**ソートシグナル**（ボーナス +12）でありフィルタではない。
- 本番実測: 43 件中ゲート通過は 8 件（18.6%）。note 13% / Google News 25%。**直近フィードの通過率は ~0%** — 通過した 8 件は大半が歴史的取得物。
- ソース拡張（V1 note タグ）は却下: 追加してもゲート通過供給は ~0 増で、低ランク filler を増やすだけ。
- これは plan 03 §3 のテーゼ「新着順フィードは定番を出せない」の実測裏付け。

**構造的ミスマッチ**: RSS は「新着」を届ける。エバーグリーン（定番・意思決定系）は定義上「新しくない」。RSS タグをいくら増やしても、抜粋を良くしても、ランキングを弄っても、**RSS はエバーグリーンを系統的に供給できない**。

## 1.5. 対象トピックの厳格な定義（選球眼の徹底）

世間の検索需要（式場探し、初期見積もり、前撮りなど）と本メディアのコア価値の混同を防ぐため、本経路が対象とするトピックと、**完全に除外すべきトピック**を厳格に定義する。

### 完全に除外すべきトピック・ソース（検索需要の罠・契約前・周縁話題）

- **式場探し・契約前の話題**: 式場見学の比較、キャンペーン、初期見積もりのカラクリや交渉術
- **前撮り・フォトウェディング**: スタジオ比較、ドレス試着、ポーズ集
- **一般的な事前準備マナー**: 両家顔合わせの挨拶手順、招待状宛名書き等の「誰が書いても同じ表面的なマナー」
- **商業オウンドメディア・アフィリエイト**: 自社サービス誘導やアフィリエイトを目的とした企業オウンドメディアやランキング記事

### 純粋に対象とするトピック（契約後・準備本番の意思決定とトレードオフ）

1. **アイテム選定・打ち合わせの取捨選択**:
   - 料理・装花・ペーパーアイテムなどのランクアップや持ち込み・手作り判断における「どこに金をかけ、どこを削ったか」の具体的な理由と結果。
2. **演出・プログラムの決定と評価**:
   - プロフィールムービー、余興、お色直しなどの演出について、「実際にやって大正解だったこと / 要らなかったと後悔したこと」。
3. **ゲスト対応・空間作りの実体験**:
   - 宿泊・お車代のリアルな分担、席次表配置やアレルギー対応など、当事者が直面した具体的な調整の判断。

## 2. 方向性（@oracle 評価により採用）

**(e) 非RSS エバーグリーン摂取経路の新設** — RSS パイプラインは一切触らず、エバーグリーン向けに設計した**独立した第2の摂取経路**を追加する。

候補経路（いずれも §10 準拠: リンクアウトのみ・本文スクレイピングなし・著作者クレジット維持）:

1. **手動キュレーションキュー**: 編集が既知のエバーグリーン URL を登録（一回設定・継続的な細流）
2. **厳選 URL の定期取得**: エバーグリーン源 URL のキュレートリストを定期 fetch（robots.txt 遵守・レート制限）
3. **ユーザー推薦フロー**: 「定番記事を推薦」受付（モデレート付き）

実装スケッチ（将来）:

```typescript
// 新テーブル: evergreen_sources (url, source_name, last_fetched, status)
// 新 cron: fetchEvergreenSources() — robots.txt 遵守、レート制限、最小メタデータのみ保存
// 既存 curatePost() を再利用 — 同一 LLM・同一ゲート・同一 §10 準拠出力
// レーンクエリ: RSS posts UNION evergreen posts（有用度スコア順）
```

リスク軽減: まず手動キュレーションキュー（自動化リスク 0）から開始、検証後にのみ自動化。

## 3. 検証実験（実装前・必須）

**目的**: 非RSS 源が RSS ベースライン（~0%）より有意に高いゲート通過率を出すことを証明する。

**プロトコル**（本番コード変更なし・~2h）:

1. 既知の良質ソース（会場ガイド / プランナー / 自治体公式 / マナー解説等、ゲートを通過しそうな内容）から**エバーグリーン候補 URL を 20〜30 件**収集。
2. 各 URL から **OGP/JSON-LD メタデータ**（og:title / og:description / og:image / JSON-LD author・datePublished）を取得 — **本文取得は行わない**（§10 準拠、V2 の OGP 方式と同一の行為）。
3. 既存 `curatePosts`（`src/lib/llm/batch.ts`）に `{ title, excerpt: ogDescription }` を渡し評価（本番と同一）。
4. ゲート通過率を RSS ベースライン（0%）と比較。

**成功基準**: 手動セットで **≥30% 通過**（RSS の 0% に対して）。達成なら非RSS 経路を検証。未達ならゲート基準自体の誤キャリブレーションの可能性（別問題）。

**検証の意義**: ソース品質と摂取機構を分離する。手動で選んだエバーグリーン URL が通れば、「RSS が間違ったパイプである」ことが確定し、ゲートが厳しすぎる/LLM が判定できないという説を退ける。

## 4. 実行順（予定）

1. **検証実験** — 本計画 §3 を実施し、非RSS 経路の妥当性を証明
2. 成功なら: 手動キュレーションキューから実装（新テーブル + 摂取 + レーン UNION）
3. その後: 自動化（厳選 URL 定期取得）は検証後にのみ

## 5. 意図的に採用しないもの

- RSS パイプラインの更なる最適化（構造的にエバーグリーンを供給できないため無駄）
- ゲート基準の緩和（§10 の安全網を崩すため不可）
- 本文スクレイピング（§10・plan 03 §4.1 により不可）
